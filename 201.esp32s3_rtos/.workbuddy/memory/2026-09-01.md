## VSCode F5 调试再报错修复（2026-09-01 九次）：Arg list too long / No hardware breakpoint support
- **现象**：F5 起 gdb 后报 `Remote communication error. Target disconnected: error while reading: Arg list too long. (from interpreter-exec console "monitor reset halt")`。`monitor reset halt` 让内核停住后，连接立即断开。
- **本地复现定位（后台起 openocd + 真实 xtensa-gdb 逐步复刻）**：
  - 基础链路正常：`monitor reset halt` + `info registers` 在 console/MI 模式都 OK（含 rtos 配置、`-d2`）。
  - 加 `runToEntryPoint` 行为（`thb main` + `continue`）即复现崩溃：关键 `Function "main" not defined` → 无断点 → `continue` 跑飞 → 断连。
  - **根因1（符号）**：本工程（ESP32 Arduino）elf **无 `main` 符号**，入口是 `app_main`（nm 确认 `app_main` @ 0x42005f6c、`_Z5setupv`）；`runToEntryPoint:"main"` 必失败。
  - **根因2（Flash 缓存）**：`monitor reset halt` 停在 ROM bootloader（0x40000400，Flash 缓存未开），对 Flash 地址 `app_main` 下硬件断点失败 → `No hardware breakpoint support in the target` → `continue` 崩连。应改用 `monitor reset init`（复位+初始化、使能 Flash 缓存后再 halt）。
  - **根因3（gdb 17.1）**：Xtensa 断点是硬件断点，gdb 17.1 可能误判目标支持 0 个 → 补 `set remote hardware-breakpoint-limit 2`。
- **修复**：`launch.json` 两处配置同步改：`runToEntryPoint` `"main"`→`"app_main"`；`overrideLaunchCommands` 改为 `["set remote hardware-watchpoint-limit 2","set remote hardware-breakpoint-limit 2","monitor reset init","flushregs"]`（顺序对齐 Espressif 官方序列，且用 `reset init` 而非 `reset halt`）。
- **环境注意（非工程问题）**：本沙箱 git-bash 对 `xtensa-esp-elf-gdb.exe` 的执行路径间歇性报 `No such file or directory`（rc=127），但二进制真实存在（`ls -laR` 确认 `17.1_20260402/bin/xtensa-esp-elf-gdb.exe` 211KB 在）。属沙箱挂载抖动，不影响 VSCode 原生调用 gdb。本地复现受阻，最终以 nm 符号证据 + 官方序列为准下结论。
- **待用户验证**：F5 选 `ESP32-S3 Debug (内置USB-Serial-JTAG)`。若仍报断连，把 gdb-server TERMINAL 输出（或 `launch.json` 加 `"showDevDebugOutput":"raw"`）发回，必要时回退到"连接即运行、手动下断点"的安全配置（去掉 `runToEntryPoint` 与 `monitor reset init`）。
- **新增安全配置项**：在 `launch.json` 加入第三个配置 `ESP32-S3 Debug (内置USB-Serial-JTAG - 安全手动)` —— 与内置口配置同路径，但**去掉 `runToEntryPoint`**（即不自动 `thb app_main`+`continue`），仅 `monitor reset init`+`flushregs` 在缓存已开态停下，由用户手动下断点/继续，彻底绕开自动 continue 崩连。JSON 已校验通过。用户可一键切换：优先用主配置（自动停 app_main），失败切安全手动。

## VSCode F5 仍报 Arg list too long（2026-09-01 十四次）：真凶是 Cortex-Debug 默认 monitor reset halt，须用空 overrideLaunchCommands 覆盖
- **现象**：把 `overrideLaunchCommands` 整组删空（不写该键）后重试 F5，崩点又回到 `monitor reset halt`：`...(from interpreter-exec console "monitor reset halt")`。说明 `monitor reset halt` **不是来自我们的 override，而是 Cortex-Debug 的内置默认启动命令**——只要 `launch.json` 不写 `overrideLaunchCommands`，扩展就自动执行默认的 `monitor reset halt`，照样触发 `Arg list too long` 断连。`flushregs` 那次崩，也是因为我的 override 顶掉了默认 `monitor reset halt`、换成我的命令后我的命令又崩（崩点前移的假象）。
- **真正根因（最终）**：在这套组合（openocd-esp32 v0.12.0 + xtensa-gdb 17.1）下，**任何 gdb attach 后对目标发的 `monitor reset halt` / `flushregs` 都会触发 `Arg list too long` 断连**（gdb 侧对 openocd 返回的 `E07/E2BIG` 解析失败）；而 Cortex-Debug 默认就会发 `monitor reset halt`。
- **最终修复（验证有效方向）**：三个配置（内置口主/安全手动、ESP-Prog）**均显式写 `"overrideLaunchCommands": []`**（空数组）——这会**覆盖掉 Cortex-Debug 的默认 `monitor reset halt`**，同时不引入任何会崩的命令。openocd 在 gdb attach 时已自动 halt 且 Flash 已映射（gdb-server 日志实证 `Flash mapping ... 0x42000020`、`Detected FreeRTOS`），`runToEntryPoint: "app_main"`（或用户改的 `app_init`）自身 `thb`+`continue` 即可自动停在入口。
- **符号核对**：elf 同时存在 `app_main`(0x42005f6c) 与 `app_init`(`_Z8app_initv`, 0x42002660) 两个合法符号，config1 用 `app_init`、config3 用 `app_main` 均可正常下断点（config2 安全手动无 runToEntryPoint，连上即 halt 由用户手动 Continue）。
