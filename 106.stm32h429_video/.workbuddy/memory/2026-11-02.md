## 决策：不实现 MP4（用户明确放弃）

2026-11-02 用户决定「放弃 mp4 处理」。已把结论固化进 `README.md` 第 5 节
「支持的文件格式」：唯一组合是 **AVI(RIFF) + MJPG + PCM**，判定点在
`video_avi.c:193`（`biCompression`）与 `:212`（`strh.fccHandler`），两条都要匹配。

评估依据（别再重复推一遍）：
- 容器层：ISOBMFF 要建 `stsz/stco/stsc/stts/stss` 五表索引，读模型从顺序 chunk
  变成按 sample `f_lseek` 随机读，FatFs on SDIO 的小随机读性能是主要风险。
- 视频层是真正的墙：MP4 基本是 H.264/HEVC。168 MHz Cortex-M4 无 L1 cache、无硬解核，
  baseline-only 的 h264bsd 解 QVGA 都只有个位数到十几 fps，480p 差 1~2 个数量级；
  参考帧 800×480 YUV420 单帧 576 KB，DPB 至少 1.1 MB，SDRAM 容量够但运动补偿的
  随机读会把有效带宽（16-bit FMC 实测常掉到 30~50 MB/s）吃光。
- 音频层：AAC-LC 额外 30~60 MHz，与视频抢 CPU 加剧。
- 采样率不是瓶颈——`s_pll_presets[]` 已覆盖 8k~192k（含 48k）。

替代路径（README 已写 ffmpeg 命令）：PC 端转 AVI/MJPEG，`-c:v mjpeg -q:v 5`
+ `-c:a pcm_s16le`。**体积代价**：480p@15fps 约 2~4 MB/s（每分钟 150~250 MB），
SD 卡需 Class 10 以上，且 SDIO 8 KB/突发 的节拍会直接决定帧率上限。
中间方案（MP4+MJPEG 轨道，只补解复用）理论上约一周，用户已明确不走。

## 新工具坑：本机 `sed -i` 会把 CRLF 改成 LF

`sed -i 's|a|b|' foo.uvprojx` 后，整个文件从 CRLF 变 LF，
`git diff` 显示 4564 行全改（`git diff --ignore-cr-at-eol` 才只剩真实差异）。
Git Bash 的 GNU sed 在这台机器上做文本模式转换，**不能用来改 CRLF 文件的单行**。
替代：python 按字节读写，且写完按 HEAD 的行尾风格归一化：

```python
body = raw.replace(b'\r\n', b'\n')
if crlf_in_head: body = body.replace(b'\n', b'\r\n')
```

判据：`git diff --numstat --ignore-cr-at-eol <file>` 应该只有真实改动行数。
