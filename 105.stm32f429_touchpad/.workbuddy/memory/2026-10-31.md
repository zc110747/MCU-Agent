# 2026-10-31 — 105.stm32f429_touchpad（USB 触摸板鼠标）

## 问题：触摸能用但"不跟手"

用户反馈光标跟随手指有拖尾/迟滞。定位后确认是**多处延迟叠加**，不是单一 bug。

### 量出来的基线（改之前）

| 指标 | 实测 |
|---|---|
| `app_ui_poll()` 循环频率 | **84 Hz**（≈12 ms 一轮，还会抖到 40 ms） |
| 鼠标 delta 计算位置 | 在这个 UI 循环里 → 光标采样率被它锁死 |
| HID 端点 `bInterval` | **8 ms**（主机 125 Hz 上限） |
| `TOUCH_POLL_MS` | 10 ms |
| `bsp_touch_scan()` 耗时 | 测出来 12.9 ms，**是假值**（见下） |

### 四个改动

1. **新建 `app/trackpad.c/.h`**：把"触摸采样 → delta → `usb_mouse_move_ex()`"整条
   链路从 `app_ui.c` 挪进 `touch_task`。UI 只消费视觉状态（圆点 + 64 点轨迹环，
   `trackpad_poll()` 带临界区读清标志，因为生产者优先级更高）。
   - `trackpad_set_area()` 由 `app_ui_create()` 注册；`app_ui_boot()` 时
     `trackpad_clear_area()`，splash 阶段样本全部忽略。
   - 语义变化：**一旦在 pad 内按下，滑出边界也继续跟随**（触摸板正常手感），
     但在按键上**按下**的那种接触永远不会进入追踪，所以不会误拖光标。
2. **HID `bInterval` 8 → 1 ms**（`app/usb_descriptors.c`）；`tud_task_ext(5)` → `2`。
   已验证配置描述符字节是 `... 10 00 01`。
3. **`TOUCH_POLL_MS` 10 → 5**，`TOUCH_RELEASE_POLLS` 3 → 4（20 ms 判定抬起，
   太紧会出现幻影 1 px 跳），`TOUCH_MAX_POLLS` 400 → 800（保持 4 s 上限）。
4. **加速度判档改成速度**：`usb_mouse_move_ex(dx, dy, dt_ms)`，阈值按
   "px / 10 ms" 算。采样率变了两次（84 → 172 Hz），按"每 tick 位移"判档会让同样的
   手速掉出高速档，表现为"越改越慢"。

### 改完实测

```
[PERF] ui=172Hz touch_scan=2717 us=793 send=17181 ep_busy=0 lat=1ms clk=168MHz
[PAD ] feeds=2716 moves=0 clicks=0 drop=0
```

- UI 循环 172 Hz（不再影响光标）
- `bsp_touch_scan()` **793 µs**（单点），5 ms 轮询 → ~172 Hz，实际受芯片 100 Hz 刷新率限制
- 报告排队延迟 **1 ms**，端点忙 **0**
- `serial_verify.py` **PASS 17 / FAIL 0**（含主机侧 `GetCursorPos` 真实位移）

## ⚠️ 可复用教训：`bsp_delay_us()` 每次调用都清零 `DWT->CYCCNT`

原实现：

```c
void bsp_delay_us(uint32_t us) {
    CoreDebug->DEMCR |= CoreDebug_DEMCR_TRCENA_Msk;
    DWT->CTRL |= DWT_CTRL_CYCCNTENA_Msk;
    DWT->CYCCNT = 0;              /* ← 每次调用都清 */
    ...
}
```

软 I2C 每个字节要调好几次它，于是任何"读两次 CYCCNT 求差"的耗时测量都被打成
垃圾：`bsp_touch_scan()` 明明 ~0.8 ms，测出来 12.9 ms，差点把我引到"优化 I2C"
的错误方向。**改成只启动一次、之后不再清零**。

> 判据：如果一个耗时测量结果大到"按这个值功能根本跑不起来"，先怀疑计时基准
> 被别人动过，而不是相信这个数字。

另外 `bsp_delay_us()` 里那三行寄存器写在软 I2C 的最内层循环里，本身就是浪费。
