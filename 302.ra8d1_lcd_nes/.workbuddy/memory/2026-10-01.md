## Phase 3 前置调研修正 + 定位 shell 失聪根因（未完全修复）

### 一、重要纠正：RA8D1 的 OSPI 就叫 XSPI，寄存器定义**现成**
之前"整个 SDK 没有 OSPI 寄存器定义"的结论是**错的**，是搜错关键字（`OSPI` vs `XSPI`）。
- `Drivers/renesas/fsp/.../R7FA8D1BH.h` 里 `R_XSPI_Type` @22073，`size=0x19c`，基址 `0x40268000`，
  与 Renesas 官方 FSP 完整版**逐字节一致**（差异仅注释空格）。
- 三个子结构 `R_XSPI_CMCFGCS_Type/_CDBUF_Type/_CCCTLCS_Type` 也齐全。
- **RA8D1 只有 1 个 xSPI 单元**（`R_XSPI_BASE`，无 `R_XSPI1_BASE`），2 个 channel。
  → 驱动必须用 **FSP v5.1.0** 的 `r_ospi_b`（`R_XSPI_*` 命名）；master 分支用 `R_XSPI0_*`（双单元
  RA8M1 命名），**编不过本器件头**。

### 二、板载串行 Flash 引脚（权威来源：参考工程 configuration.xml）
**单线 SPI 模式（custom.free / om_sio0..3）**，不是 8 线：
| 信号 | 引脚 |
|---|---|
| OSPI_CS0 | **P107** |
| OSPI_SCLK | **P808** |
| OSPI_SIO0 (MOSI) | **P100** |
| OSPI_SIO1 (MISO) | **P803** |
| OSPI_SIO2 (WP) | **P103** |
| OSPI_SIO3 (HOLD) | **P101** |
- 之前记的 `OSPI_CS=P104` 是错的。
- 与现有 SDRAM 引脚唯一冲突：**P100**（原 BUS）→ 已改 OSPI。

### 三、`r_ospi_b` 的读路径约束（关键设计约束）
该驱动的 API **不是流式 Flash API**：
- `DirectRead()` 是 stub，返回 `FSP_ERR_UNSUPPORTED`
- `DirectTransfer()` 一次最多搬 `CDBUF[0]` 的 16 字节
- `Write()`（DMAC 关）字面就是 `*(uint64_t*)p_dest = *(uint64_t*)p_src;`
  —— **对 XIP 窗口的内存写**，8 字节粒度，且**低 3 位地址被屏蔽**
- → **唯一大块读路径是 XIP 内存映射**（`0x80000000`）
  ⇒ `OSPI_B_CFG_XIP_SUPPORT_ENABLE=1`；读=普通 load，写=erase 后普通 store，擦除走驱动。
  写前必须 `XipExit`，写完 `XipEnter`。

### 六、**关键根因：FSP ISR 未告知 RT-Thread 自己在中断上下文**
`BSP_CFG_RTOS=2`（"其他 RTOS"）→ `FSP_CONTEXT_SAVE/RESTORE` 展开为**空**
（只有 ThreadX 才展开）。而 RT-Thread 的 `rt_sem_release()` 结尾是：
```c
if (rt_interrupt_get_nest() == 0) rt_schedule();   // 在 ISR 里非法！
else rt_thread_switch_interrupt_flag = 1;          // 正解：延到 ISR 退出
```
嵌套计数恒为 0 → ISR 里直接 `rt_schedule()` → 等待线程被标 ready 但**永不恢复**。

**症状**：字符进得来（ring 填满、信号量计数涨），但 msh 线程再也不跑。
- 证据：`g_bsp_diag` 快照（SysTick 里写）显示
  **`rt_thread_ready_priority_group = 0x00000000`**、`cur_thread = tidle0`、`rx_pending = 24`。
- 三个动态线程（tshell/main/led）TCB 的 stat/prio 读数全为 `0xfffffff7`（可疑，待复核），
  `tidle0`（静态）干净 —— 动态 vs 静态的差异值得继续查。

**已做的修复**：`bsp/ra8d1-vision-board/bsp_isr.c` 新增
`bsp_uart_rxi_isr` / `bsp_glcdc_line_isr`，**包 `rt_interrupt_enter()/leave()`**；
`gen/vector_data.c` 槽 0/1 改指向包装函数（已验证 ELF 向量表：槽0=0x02002051、
槽1=0x02002061，thumb 位正确）。
**但烧录后 shell 仍然失聪** → 说明该修复**不是**（或不只是）根因，或还有第二处问题。

### 七、另一个已修的真 bug：UART TX FIFO 自旋无上限导致掉字节
`bsp_uart_putc` 原来 `while (fifo_depth <= FTSR_b.T) ;` **无超时**。
实测所有被截断的输出都停在 **16 字节 = TX FIFO 深度**。
→ 改为带 `BSP_UART_TX_SPIN_LIMIT` 的有限自旋（超时丢字节而非挂死）。
修复后启动日志**不再截断**，但 shell 交互仍无响应。

### 九、**已解决：shell 失聪 + 串口输出截断**（Phase 2 遗留两条技术债）

### 十二、用户指令修正：**CS 是 CS1 → P104，不是 CS0 → P107**
此前从参考工程 `pin_data.c` 读到的 `P01_PIN_07` 是错的。按用户指令改为：
```
OM_CS1 = P104    OM_SCLK = P808    OM_SIO0 = P100
OM_SIO1 = P803   OM_SIO2 = P103    OM_SIO3 = P101
```

**原理图双向确证（`documents/Vision_Board_schematic.pdf`）**：

| 网络 | MCU ball | MCU 引脚 | U14 引脚 |
|---|---|---|---|
| OM_CS1 | L1 | **P104** ✅ | 1 `~CE` |
| OM_SCLK | R1 | P808 | 6 `SCK` |
| OM_SIO0 | N1 | P100 | 5 `SI_IO0` |
| OM_SIO1 | N3 | P803 | 2 `SO_IO1` |
| OM_SIO2 | L2 | P103 | 3 `~WP_IO2` |
| OM_SIO3 | M2 | P101 | 7 `~HOLD/~RST_IO3` |

U14：pin8 `VCC`=+3.3V（C77 100n 去耦）、pin4 `GND`。**器件有贴片、有供电、CS=OM_CS1。**
⇒ **用户给的引脚 100% 正确**，此前 P107 结论作废。

### 十三、代码修正（3 处）

### 十四、实测裁决：**控制器配置正确，器件不驱动 MISO（硬件层）**

**SWD 直读 PFS（复位后立即，未经 bit-bang 污染）**：

SIO3 P101 0x1C010000  PSEL=1C PMR=1

扫描全仓 0..12 端口，**恰好这 6 个引脚 PSEL=0x1C(OSPI)** —— 引脚复用完全正确。

**`ospi regs`（CS1 真实寄存器）**：全部与驱动应有值吻合
`LIOCFGCS1=0`（1S-1S-1S 正确）、`CMCFG1_0=0x00f00008`、`CMCFG1_1=0x00000300`(RDCMD=0x03)、

`COMSTT=0`、`MSTPCRB=0xffbeffff`(bit16=0 已解停)。

**关键取证：MISO 上拉判定**
- P803 作为 GPIO 输入（无内部上拉）恒 **0**
- **使能内部上拉后 → 恒 1，稳定不翻转** ⇒ **线路未短路，是器件根本没驱动**

**调试器手动 SPI（绕过全部固件时序嫌疑）**，WP/HOLD 主动拉高、CS=P104：
| 命令 | 结果 |
|---|---|
| `0x9F` JEDEC ID | `FF FF FF`（24 bit 全 1）|
| `0xAB` 释放掉电/读 ID | `FF FF FF` |
| `0x05` 读状态寄存器 | `FF`（应为 0x00）|
| `0x90` 读厂商/器件 ID | MFG=`FF` DEV=`FF` |

**U14 从未对任何命令作出响应，MISO 全程高阻**。可能原因按概率：
1. **U14 未实际贴片**（原理图有、实物无 —— 参考工程全程用 SD 卡存游戏，从未用过 OSPI Flash）
2. VCC(+3.3V) 或 GND 未连通（C77 也未贴）

4. WP/HOLD 被外部拉低（已排除：主动拉高后仍无响应）

**需用户上机确认**：① U14 是否有实物；② 万用表量 U14 pin8 对 GND 是否 3.3V；
③ 量 pin1 `~CE` 在复位后是否被 MCU 拉高。

## 第三轮：取证工具链自查 —— 推翻上一轮的两条关键"证据"

上一轮把结论定在"硬件层器件不响应"，依据是「SWD 读 PFS 全 0」和「MISO 上拉体检」。
本轮对**测量工具本身**做了验证，发现前者是**假证据**，据此重新界定结论边界。

### 一、SWD 读外设寄存器不可信（已验证）

同一时刻两个读数直接矛盾：

| 项 | 固件自读（权威） | pyOCD SWD 读 |
|---|---|---|
| `P104` PmnPFS | `0x1C010C00` PSEL=0x1C PMR=1 | `0x00000000` |
| `MSTPCRB` | `0xffbeffff`（XSPI bit16=0，时钟**开**） | `0xffffffff`（时钟"关"） |
| `R_XSPI` 全部 | 非零（见 `ospi regs`） | 全 `0x00000000` |

- `bsp_ospi_init()` → `R_OSPI_B_Open()` → `R_BSP_MODULE_START(FSP_IP_OSPI,0U)`
  清 `MSTPCRB` bit16；固件读到 `0xffbeffff` 与之吻合。**时钟确实是开的。**
- ⇒ pyOCD 会话读 RA8D1 外设空间返回全 0，是**测量工具的问题**，不是外设状态。
  上一轮"PFS 复用正确"碰巧结论对（后来固件自读证实），但**那条证据本身作废**。

**新增 `ospi pfs` 命令**：由固件自己回读 6 个 `PmnPFS`。
实测全部 `PSEL=0x1c PMR=1 OK`（CS1=P104 / SCLK=P808 / SIO0=P100 / SIO1=P803 / SIO2=P103 / SIO3=P101）。

### 二、`read_regs.py` 修正（历史 bug）

- 引脚表仍是旧的 **P107/CS0** → 改为 **P104/CS1**。
- `XSPI_REGS` 偏移错得离谱（曾把 `CMCFGCS1` 写成 `0x014`、`COMSTT` 写成 `0x184`
  后又误改成 `0x164`、`INTE` 写成 `0x198` 后又误改成 `0x178`）。
  **最终以 `R7FA8D1BH.h` 结构体成员注释为准**：
  `CMCFGCS[2]@0x10`(stride 0x10) `LIOCFGCS[2]@0x50`(stride 4) `CDBUF[4]@0x80`(stride 0x10)
  `CCCTLCS[2]@0x130`(stride 0x20) `VERSTT@0x180` `COMSTT@0x184`
  `CASTTCS[2]@0x188`(stride 0x20) `INTS@0x190` `INTC@0x194` `INTE@0x198`。
  脚本已在 PFS/MSTP 段打印"此读数不可信"警告。
- 固件 `bsp_ospi_reg_dump()` 里 `COMSTT` 原读 `0x164`（**不是任何寄存器**）→ 改 `0x184`。

### 三、CS 活动探针：两次误判，最终承认"固件侧测不出"

试图判定"CS 到底有没有拉低"，连错两版，都是**仪表未先对已知答案校验**：

1. **把 pad 掰成输入去读**（外设仍在驱动该 pad）
   → 读到低电平，报 "CS 有拉低"。**假阳性**：竞争态读数，无命令时也读低。
2. **改用 `COMCFG.ECSINTOUTEN` + `COMSTT.ECSCS`**
   → 读到 `idle_high=1 cs_asserted=0`，报 "CS 从不拉低"。**同样无效**：
   `ECSINTOUTEN` 是 *ECS/INT **Output** Enable*（把信号**输出到引脚**），
   不是把 ECS 引到状态位；`COMSTT` 在 64 次连续命令中**恒为 `0x00770000`，一位未动**
   → **它根本不跟踪总线**。读数与"CS 状态"无关。

**最终版本**（`ospi cs`）只报告原始事实，不下结论：
```
ospi cs: idle=0x00770000 min=0x00770000 changed=0 (idle_high=1)
ospi cs: COMSTT did not move across 64 commands -> it does not track the bus;
         CS state NOT determinable from firmware
```

### 四、当前结论（按证据分级）

**有正面证据（固件/源码自证）**：
1. 6 个引脚复用正确：`PSEL=0x1C`、`PMR=1`（固件自读）。
2. xSPI 时钟已解禁（`MSTPCRB=0xffbeffff`）。
3. 控制器寄存器配置与驱动预期一致：`LIOCFGCS1=0`（1S-1S-1S 正确值）、
   `CMCFG1_0=0x00f00008`、`CMCFG1_1=0x00000300`(RDCMD=03)、`CMCFG1_2=0x00000200`(WRCMD=02)、
   `BMCTL0=0xff`(CS1 访问位=0b11)、`CDCTL0=0x8`(CSSEL=1→CS1)、`COMSTT=0x00770000`。
4. 手动命令路径**正常返回**（`ospi init` 返回 `0x6=FSP_ERR_UNSUPPORTED`，是容量=0 的
   主动返回，**不是 `FSP_HARDWARE_REGISTER_WAIT` 死等** → `CMDCMP` 曾置位）。
5. `bsp_ospi_bitbang_id()` 手打 `0x9F`（WP/HOLD 拉高）→ `00 00 00`。

**仍无有效证据**：
- **CS 是否真的拉低过 —— 固件侧三种手段全部无效**，无法判定。
- 器件是否贴片 / 供电 / `~CE` 连通 —— 上一轮仅凭"SWD 读 PFS"和"pad 竞争读数"推进，
  这两条已作废，所以**上一轮的"硬件层裁决"证据强度不足，需降级为待验证假设**。

### 五、下一步（必须换仪表）

固件侧已到极限。可用手段只剩**外部仪表**：

| 手段 | 测什么 | 判据 |
|---|---|---|
| 万用表 | U14 pin8 `VCC` 对 GND | ≈3.3V → 有供电 |
| 万用表 | U14 pin4 `GND` 对 MCU GND | 导通 → 共地 |
| 万用表/示波器 | U14 pin1 `~CE` 在 `ospi id` 执行瞬间 | 出现下拉脉冲 → CS 到达器件 |
| 示波器 | P808 `SCLK` 在 `ospi id` 瞬间 | 有 8+ 个时钟沿 → 控制器在发时钟 |
| 逻辑分析仪 | 四线同时抓 | 一次性判定时序与 CS |

若 CS/SCLK 有波形而器件仍 `00 00 00` → 器件问题（未贴/损坏/WP 被拉低）。
若 CS 无波形 → MCU 侧 / 走线问题，回到 `LIOCFGCS1` 的 `CSMIN/CSASTEX` 与 pad 驱动能力排查。
