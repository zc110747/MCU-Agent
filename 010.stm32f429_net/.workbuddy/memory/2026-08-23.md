## 第三十波：Telnet IAC 协商修复 + Python 测试脚本（IP 192.168.10.99）

### 问题（用户用 Windows 自带 telnet.exe 实测反馈）
1. 连接后 banner 前残留 `!"'` 乱码
2. 所有指令无本地回显（敲的字符屏幕不显示）
3. 指令无输出（help/list 等无返回）
4. 用户要求：功能下载后也用 telnet 接口脚本测试（python 支持情况）

### 根因
- 旧 IAC 状态机有 bug：把 `255 255`（转义）误判后"fall through 当数据字节"漏进数据路径，
  客户端（Windows telnet / PuTTY）的 WILL/DO 协商应答被当数据 → `!"'`；
  回显/SGA 协商混乱 → 客户端未进入"服务端回显"模式 → 输入的字符不显示、输出协商不稳。

### 修复（app/telnet_shell.c）
- 重写 IAC 状态机为 5 态（0 正常 / 1 IAC 后等命令 / 2 SB 子协商 / 3 等选项字节 / 4 等 SE），
  全部用每任务局部变量（iac_state/iac_verb，非 static），杜绝并发污染。
- 新增 `telnet_reply_option()`，按 RFC854 对称应答：客户端 WILL/WONT→我们 DONT；
  DO→仅 ECHO/SGA 回 WILL，其余 WONT；DONT→WONT。SB...IAC SE 子协商整段吞掉。
- `telnet_conn_cleanup()` 改为：先排空对端残包(300ms)→`netconn_close` 发 FIN→延时 200ms
  让 "Bye!" 与 FIN 落线→`netconn_delete`。消除 exit 时内核发 RST（之前 Python 收到 10054）。

## 第三十一波：Telnet 接收 NUL(0) 字节导致命令截断修复

### 问题（用户真机测试发现）
- telnet 接收循环 `line[len++] = (char)c;` 会把**任意**字节（含 c==0 的 NUL）写入 line 缓冲区。
- 某些 telnet 客户端会在数据流中夹带**概率性 NUL**（0）字节；一旦 NUL 写入 line，
  `str*` 函数遇 `\0` 即终止，命令被截断成空串/乱串 → `help` 等命令无输出（MobaXterm 也复现，
  证实是嵌入式端问题，非客户端问题）。

### 修复（app/telnet_shell.c 接收循环正常数据路径）
- 在写入 line 前新增分支：`else if (c == 0) { /* NUL: 不写入、不回显 */ }`，
  放在 `else if (len < TELNET_LINE_MAX - 1) { line[len++] = (char)c; ... }` 之前。
- 注意：IAC 转义字节 `line[len++] = (char)255;` 是合法数据字节（255），与此 NUL 过滤无关，不动。

### 测试脚本扩展 tools/telnet_test.py
- 新增 `send_raw()`（可发含 NUL 的裸字节）+ `--nul` 模式 `run_nul()`：
  测试 `he\0lp`（NUL 居中）、`\0help`（NUL 前缀）、`help\0`（NUL 后缀）三种注入，
  均期望正确解析为 help 并输出 Commands 列表；另加"NUL 轰炸后正常 help 仍可用"+exit。

### 验证结果
- Debug 273676B/26.10%、Release 297384B/28.36% FLASH，双构零警告（仅 RWX 良性提示）
- 烧录后真机：
  - `--nul` 6/6 PASS（NUL 居中/前缀/后缀均正确执行 help，无 garbage/Unknown）
  - 标准全命令套件 16/16 PASS（help/hw/dev/version/net/history/beep/led/exit 全有输出）
- 结论：NUL 过滤修复后，telnet 命令解析对客户端夹带 NUL 免疫；help 无输出问题根因即此。

## 第三十波：HTTPS 卡顿修复（并发 + 握手缓存 + 60s 保活）

### 用户现象
网页复杂/更新时界面刷新、按键动作直接卡住。背景诉求：mbedTLS 握手要缓存一段时间（一分钟未通讯才断开）。

### 根因（旧架构）
1. `https_server.c` 是**单任务串行**：一个 httpsd 任务 accept 后串行服务，浏览器并发 6 连接全排队；且握手后只 read 一次请求就 close，复杂页面每个资源重握手 → 串行瓶颈。
2. 重构时暴露：mbedTLS **未开 `MBEDTLS_THREADING_C`**，多 `mbedtls_ssl_handshake` 并发踩内部全局状态 → 只有一个握手能成功，其余超时/RST；`g_rng_state` 全局 RNG 并发竞争。
3. idle 超时漏设 `netconn_set_recvtimeout` → `netconn_recv` 永久阻塞 → 60s 保活从不触发（BIO 把 ERR_TIMEOUT 误当 EOF）。

### 修复
- `web_serve.c/.h`：`web_serve` 增 `int keepalive` 参数；HTTPS 传 1 时响应头改 `Connection: keep-alive` + `Keep-Alive: timeout=60`（HTTP 仍传 0 保持原 close 行为）。
- `https_server.c` 重构：
  - `g_rxbuf/g_rxlen/g_rxpos` 改 per-connection（挂 `https_conn_ctx`），消除多连接全局共享踩踏。
  - listener 只 accept，每连接 `xTaskCreate` `https_conn_task`（栈 3072、优先级 3），互斥计数上限 `HTTPS_MAX_CONNS=4`。
  - `https_conn_task`：handshake 前 `s_hs_gate` 互斥（**握手串行化**，规避非线程安全）→ 请求循环（keep-alive 复用同一 TLS 会话，多次 web_serve）→ 60s idle 超时（`netconn_set_recvtimeout(1000)` 轮询 + last_active 比较）才 close_notify+优雅关闭。
  - `https_rng` 加 `s_rng_mutex` 保护全局 RNG。
  - `https_bio_recv` 区分 `ERR_TIMEOUT`→`WANT_READ`（轮询 idle）vs 其他→EOF。
- `mbedtls_pool.h` 新增（暴露 `MBEDTLS_POOL_SIZE` + `mbedtls_heap[]` 声明）；堆 32KB→**256KB**（SDRAM 充裕，留并发握手碎片余量）。
- `lwipopts.h`：`MEMP_NUM_NETCONN` 8→12（HTTPS4+telnet3+HTTP1 余量）、`PBUF_POOL_SIZE` 64→96。

### 验证（真机 192.168.10.99）
- Debug 274144B/26.78%、Release 约 29.7% FLASH（bss 含 256KB SDRAM 池），双构零警告（仅 RWX）
- `tools/https_test.py` 3/3 PASS：单连接 200+keep-alive 头 / 同连接复用第 2 请求 / 4 并发×3 请求 12/12
- 60s idle 超时：t=60.0s 服务端干净 FIN 关闭（复测 True）
- telnet 16/16、HTTP/80 close 行为 均无回归

### 结论
卡顿根因是单任务串行 + mbedTLS 非线程安全并发握手。改为"每连接独立任务 + 握手串行化 + keep-alive 复用 + 60s 保活"后，复杂页面并发刷新/按键即时响应，握手缓存生效。
