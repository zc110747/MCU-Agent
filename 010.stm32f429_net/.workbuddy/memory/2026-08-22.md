## 两个关键 Bug（都是"推断 vs 实测"的教训）

### 1. 链接脚本内存尺寸错误 → 启动即 HardFault
**症状**：烧写 verify OK，但复位后立刻停在 HardFault_Handler。
HFSR=0x40000000 (FORCED)、CFSR=0x00001400 (PRECISERR+UNSTKERR)、MSP=0x20040000。

**根因**：`STM32F429IGTx_FLASH.ld` 写的是 `RAM LENGTH = 256K` / `_estack = 0x20040000`，
但 STM32F429IG 真实连续 SRAM 只有 **192K**（SRAM1 112K + SRAM2 16K + SRAM3 64K，
0x20000000~0x2002FFFF）。CCM 64K 在 0x10000000，不连续且 ETH DMA 访问不到。
初始栈顶落在未映射地址 → 第一次压栈就总线错误。
FLASH 也写错了（2048K，实际 1024K）。

**实测方法**（别靠推断，芯片手册也可能记错型号）：
```
openocd ... -c "mdw 0x2002FFFC"  # 可读
            -c "mdw 0x20030000"  # ERROR -> 边界在此
```
注意：我第一轮曾推断成 128K，也是错的。只有实测靠得住。

**附带修复**：CMake 没把 .ld 当依赖，改了不会重新链接（`ninja: no work to do`）。
已加 `set_target_properties(... LINK_DEPENDS ${LINKER_SCRIPT})`。

### 2. 硬件校验和卸载破坏 IP 分片
**症状**：`ping -l 1472` 通，`ping -l 1473` 100% 超时。悬崖式失败，正好在分片边界。

**根因**：`CHECKSUM_BY_HARDWARE=1` + `TxConfig.ChecksumCtrl =
ETH_CHECKSUM_IPHDR_PAYLOAD_INSERT_PHDR_CALC`。MAC 靠扫描"当前这一帧"来插入 L4 校验和；
lwIP 分片后每帧只含部分载荷，MAC 对分片算校验和 → 值错误 → 对端静默丢弃。

**排查关键**：先用 `gcc -dM -E` dump 实际生效宏，确认 IP_REASSEMBLY/IP_FRAG 都是 1，
排除配置问题后才锁定校验和。（`#pragma message` 在 `-E` 下被原样透传不求值，不能用。）

**结论**：无法做"按包混合"——CHECKSUM_GEN_* 是编译期全局开关，lwIP 无法只为分片算校验和。
已改为软件校验和（代价 +640B flash，ping RTT 无可测差异），并加 `ETH_USE_HW_CHECKSUM`
单一开关同时驱动 lwipopts.h 和 ethernetif.c——两处脱钩正是本 bug 成因。

## 清理掉的死配置（易误导）
- `IP_FRAG_USES_STATIC_BUF` / `IP_FRAG_MAX_MTU`：lwIP 1.4 遗留，2.x 已移除
- `ETH_RXBUFNB` / `ETH_TXBUFNB`：旧 HAL ETH 驱动的，现代驱动只读 ETH_RX/TX_DESC_CNT
- 实际生效的 RX 缓冲数是 ethernetif.c 里的 `ETH_RX_BUFFER_CNT`(20)

## 环境坑
- Git Bash 吞掉 curl 的 `-w "%{http_code}"` 花括号，输出成 `code=%http_coden`，
  导致压测误判全失败。改用响应体 grep 判定。
- 原生 arm-none-eabi-gcc 看不到 MSYS 的 `/tmp` 和 `/dev/null`，临时文件要放项目内。
- ipconfig 输出是 GBK，需 `iconv -f GBK -t UTF-8`。
- openocd (sysprogs 0.12.0) 用 `transport select swd`，不是 `hla_swd`。

## 22日第二波：FreeRTOS 化重构 + SDRAM（用户要求）
- 用户要求：回退 TLS，FreeRTOS 化 LwIP（third_party/FreeRTOS-Kernel V11.1.0）+ SDRAM 内存池
- SDRAM: bsp_sdram.c（FMC Bank1, W9825G6KH 32MB, 90MHz, 引脚按 stm32f4_hw.md）+ 自检通过
- 内存布局：ram_heap 128KB @0xC0000000 (lwip mem heap)、ucHeap 512KB @0xC0020000 (FreeRTOS heap)
  → 链接脚本 SDRAM region + NOLOAD 段；RX_POOL/memp 池必须留 SRAM（ETH DMA 写 SDRAM 分片丢包）
- LwIP 多线程：NO_SYS=0, LWIP_NETCONN=1, tcpip_init + tcpip_input(ISR) + sys_arch.c(FreeRTOS)
- HTTP: netconn API + 独立任务（先 recv 再响应，否则 close 发 RST）
- HAL 时基 TIM7（SysTick 给 FreeRTOS）
- 排障三大坑（详见 MEMORY.md）：
  1) V11 INCLUDE_* 默认 0 + port.c 需 softfp + 向量表必须直指 port 函数（port.c assert 343）
  2) 调度器前 xTaskCreate 残留 BASEPRI=0x50 → TIM7/HAL_Delay 卡死 → tcpip_init 后 __set_BASEPRI(0)
  3) ISR 里 SYS_ARCH_PROTECT 不能 vPortEnterCritical → xPortIsInsideInterrupt 跳过
- 验收：SDRAM 32MB OK、ping 20/20、ICMP 32~16000B 全通、HTTP 30/30、CFSR/HFSR=0
- Debug/Release 双构零警告；README.md 已更新

## 22日第四波：ERR_CONNECTION_RESET 根因 + HAL_Delay 全清除（用户要求）
- 用户浏览器报 ERR_CONNECTION_RESET（之前能通），curl HTTP/HTTPS 全 RST（exit 56/35）
- 排查：CFSR=0、ping 通、PC 在 LwIP 主循环 → 非 fault 非死锁
- 根因：**BASEPRI 残留复燃**——main.c 在 vTaskStartScheduler 前连续 xTaskCreate
  （tcpip_thread + httpd + httpsd），只清了 tcpip_init 后的，server init 后漏清
  → httpd/httpsd 任务静默未启动 → 端口无 LISTEN → SYN 收 RST
- 修复：每个调度器前 xTaskCreate 后都 __set_BASEPRI(0); __enable_irq()
- 用户要求：不要用 HAL_Delay，用 vTaskDelay → 新增 bsp/bsp_delay.h
  （DWT CYCCNT 忙等，header-only 不改 CMake）；调度器前 3 处 HAL_Delay
  （PCF8574 50ms×2 + SDRAM 1ms）改 bsp_delay_ms/us；任务内本来就是 vTaskDelay
- 应用层 HAL_Delay 零调用达成；Debug/Release 双构零警告（仅 RWX 良性）
- 验收：HTTP 15/15、HTTPS 15/15（DWT 延时下 SDRAM 初始化/PHY reset 正常）
- 技能 8.4 更新（每个调度器前 xTaskCreate 后都要清）+ 新增 8.9（DWT 忙等）

## 22日第五波：HTTPS 8.88s 慢 → ECP 优化（用户报告）
- 用户：浏览器 https 8.88s 才出页面，问是否 TLS 任务优先级问题
- curl 时间分解：TCP 2ms、TLS 握手 4.88s（Debug）/ 3.67s（Release）稳定无波动 → 计算瓶颈
- **不是优先级问题**：httpsd=3 与 tcpip_thread=3 同级时间片轮转不饿死（tcpip 无包阻塞让出）
- 根因：mbedtls_config.h 白名单配置缺 ECP 加速宏 → P-256 通用模约减慢 5-10 倍
- 修复：加 MBEDTLS_ECP_NIST_OPTIM + WINDOW_SIZE=6 + FIXED_POINT_OPTIM=1
- 结果：Debug 4.88→0.83s、Release 3.67→0.64s（约 6 倍）；FLASH +18KB（window6 表）
- 双构零警告（仅 RWX）；README 新增"HTTPS 握手性能"表格；技能 9.5 新增
- 后续可选：MBEDTLS_HAVE_ASM（M4 umull asm）再降 20-40%，需验证 3.x 支持

## 22日第六波：HTTPS 再优化（用户要求更快 1.46s→0.8s）
- 用户实测浏览器 1.46s；固件 curl 单连接 0.79s（Debug）
- 加 MBEDTLS_HAVE_ASM（M4 umull/umlal DSP asm，bn_mul.h ARMv6+ 路径）：0.83→0.79s
- 试 X25519（CURVE25519_ENABLED + mbedtls_ssl_conf_groups 优先）：**反而 1.07s**——
  mbedTLS 3.6 无 Everest，走通用 Montgomery ladder 比 NIST 优化 P-256 慢 → 回退
- **1.46s 真因**：浏览器并发请求 / + /favicon.ico 两个连接，httpsd 单任务串行握手
  （实测 0.80+0.82=1.62s）→ HTML 加 <link rel=icon href="data:,"> 消除 favicon 请求 → 单握手
- 最终：Debug 0.79s / Release 0.64s（P-256 + NIST/WINDOW6/FIXED + ASM）
- 技能 9.5 补充：HAVE_ASM 收益小、X25519 无 Everest 时更慢（实测否决）、favicon 双连接坑
