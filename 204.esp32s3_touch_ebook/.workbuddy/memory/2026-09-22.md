# 2026-09-22 — 204.esp32s3_touch_ebook 立项，Phase 0+1 落地

## 做了什么

从零建立 ESP-IDF + LVGL 9 工程（Waveshare ESP32-S3-Touch-LCD-4.3B，800×480 RGB），
按提示词 `doc/prompter-step1.md` 完成 **Phase 0（骨架）+ Phase 1（LCD bring-up）**，
构建零警告零错误，提交 `b32910b`（54 文件 / 9591 行）。

## 关键结论（后续 Phase 会反复用到）

- **无撕裂渲染的机制已从源码确认，不是照抄配置**：
  `avoid_tearing=1` 时 `esp_lvgl_port` 用 `esp_lcd_rgb_panel_get_frame_buffer(panel,2,...)`
  把面板的两块 FB 直接交给 LVGL，`buffer_size` 被强制为 `hres*vres`；
  flush 时 `esp_lcd_panel_draw_bitmap` 认出指针属于内部 FB（`draw_buf_copy_to_fb=false`）
  只切换 `cur_fb_index` → **LVGL 绘制缓冲 = 面板 FB，零额外分配、零像素拷贝**。
- 用 **direct mode** 而非 full_refresh：`lv_refr.c` 的 `refr_sync_areas()` 会把上次改动区域
  重放到另一块缓冲以保持双缓冲一致，只重绘脏区（ebook 场景几乎全静态）。
- **`fb_behind_cache` 是自动推导的**（`ext_mem_cache_line_size>0`），因此
  `CONFIG_ESP32S3_DATA_CACHE_LINE_64B=y` 是硬前提——它决定驱动是否对 PSRAM FB 做 C2M
  cache 同步。少了这个征兆是"随机位置显示旧像素"。
- 面板 5-6-5 接线 → FB 位映射固定：bit15..11→R7..R3、bit10..5→G7..G2、bit4..0→B7..B3。
- 背光接 CH422G EXIO2（AP3032 CTRL），**板上无 PWM 调光线**，只能开/关，不做假亮度接口。
- CH422G 无寄存器：命令写在 **I²C 地址相位**（0x24 模式 / 0x38 写 IO / 0x26 读 / 0x46 写 OC）。

## 架构约定（已落地，改动前先读 README）

# 2026-09-22（续 2）— "整体位移"根因定性：RGB DMA 带宽失步，**不是布局、不是 porch**

用户第二次反馈："界面仍然是整体右移，右边像素点部分出现在左边"。
**没有再猜，转为取证 + 官方真值核对**，结论如下。

## 根因（三条独立官方证据指向同一处）

1. `esp_lcd_panel_rgb.h` → `esp_lcd_rgb_panel_restart()` 原文：
   *"the LCD controller is out of sync with the DMA because of insufficient bandwidth.
   To save the screen from a **permanent shift**"* —— 官方对"固定位移"的命名就是它。
2. `esp_lcd_panel_rgb.h` → `bounce_buffer_size_px`：
   *"DMA fetching from DRAM bounce buffer is much faster than PSRAM frame buffer."*
3. Kconfig `LCD_RGB_RESTART_IN_VSYNC`：
   *"Only need to enable it when … the DMA can't deliver data as fast as the LCD consumes it."*
   驱动源码注释亦写：*"Reset the GDMA channel every VBlank to stop permanent desyncs"*。
4. 旁证（同板工程师，repo `jayheavner/yoto-esp32-controller` 的 CLAUDE.md）：
   `hsync_back_porch` 8→30 **"had NO effect — the flicker is temporal underrun"**，
   且他们专门做了"注入 PSRAM 总线负载 → 观察边缘劣化/恢复"的端点。

带宽账：FB 768000B 只能放 PSRAM；39Hz 下 **仅 DMA 就 30MB/s**，还要与 CPU 渲染写入、
cache 行回写、`SPIRAM_FETCH_INSTRUCTIONS/RODATA` 取指**抢同一条总线**。

## 官方真值（github.com/waveshareteam/ESP32-S3-Touch-LCD-4.3B）

`examples/ESP-IDF/09_lvgl_v9_demo/components/waveshare_rgb_lcd_port.c`（800x480 分支）：

| 项 | 官方 | 我们（改前） |
|---|---|---|
| hsync pulse / back / front | 4 / 8 / 8 | 8 / 16 / 16 |
| vsync pulse / back / front | 4 / 8 / 8 | 8 / 16 / 16 |
| `pclk_active_neg` | 1 | 0（**保留 0**，见下） |
| `bounce_buffer_size_px` | `800 × 10 行` = 8000 | **0** |
| `sram/psram_trans_align` | 4 / 64 | 无（**IDF 6.x 已移除该字段**） |

引脚表与 `board_config.h` **逐条一致**（含 DATA0..15 = 14,38,18,17,10,39,0,45,48,47,21,1,2,42,41,40）
→ 引脚没错，错的是 DMA 配置与时序常量。

`pclk_active_neg` 故意保留 0：采样沿错会表现为**逐像素噪声/鬼影**，而当前画面是干净的、
只是被位移 → 现有极性已经锁存正确，不去动一个已验证的参数。

## 改了什么

1. `board_config.h`：时序对齐官方 4/8/8；新增 `BOARD_LCDPCLK_ACTIVE_NEG`、
   `BOARD_LCD_BOUNCE_BUF_LINES=10` / `BOARD_LCD_BOUNCE_BUF_PX`；把根因与两条解法的
   原文证据写进注释（唯一真源要能自证）。
2. `display_driver.c`：`bounce_buffer_size_px = BOARD_LCD_BOUNCE_BUF_PX`。
   约束已验：`fb_size % bb_size == 0` → 768000 % 16000 = 0（每帧 48 块）。
3. `lvgl_port.cpp`：`rgb_cfg.flags.bb_mode = true`（原先注释写着 "no bounce buffer"）。
   **必须与 `bounce_buffer_size_px != 0` 成对**：bb_mode 只切换释放绘制缓冲的事件
   （bb → `on_frame_buf_complete`，非 bb → `on_vsync`），不一致就是等一个永不到来的事件。
4. `sdkconfig.defaults`：`CONFIG_LCD_RGB_RESTART_IN_VSYNC=y` 作兜底。
5. 新增**渲染速率探针**（验收块内）：`LV_EVENT_RENDER_READY` 计数，每 5s 打印 `RATE renders = n/s`。
   取 RENDER_READY 而非 REFR_READY 的理由：前者只在真的画了东西时才发，空屏报 0 而不是定时器速率。

## 已验证的约束（动手前查过，避免烧一版就 abort）

- `register_event_callbacks` 对回调的 IRAM 检查被 `#if CONFIG_LCD_RGB_ISR_IRAM_SAFE` 包着，
  我们**未启用** → 回调可放 flash，不会 `ESP_ERR_INVALID_ARG`（否则 esp_lvgl_port 的
  `ESP_ERROR_CHECK` 就是开机 abort）。
- bb 模式下 `draw_bitmap` 收到面板自己的 FB 时**只切换 `cur_fb_index`**（行 761），
  反弹填充是 CPU 拷贝（行 1042，顺带天然解决 cache 一致性），**不会退化成每帧 768KB 额外拷贝**。
- `avoid_tearing` + `num_fbs=2` + bb 模式可共存，驱动有 `bb_fb_index` 专门处理。

## 方法论教训（写进 skill `esp32-platform-notes`）

- 相机预览截图有缩放与斜拍，**不要**用它做绝对像素测量；我用它量出的数字自相矛盾
  （品红线检测出三条、色块位置与四角定义不符）。改用"标尺相对玻璃边界"的关系判断。
- `sdkconfig.defaults` 只在 `sdkconfig` **不存在**时生效 —— 改完 defaults 必须删 `sdkconfig`
  重建（launcher 里已有告警守卫，但只告警不自愈，设计如此）。

# 2026-09-22（续 3）· "仍整体右移"的真正根因：两条修复互相拆台

## 结论：先前"把两条修复同时打开"是错的，`RESTART_IN_VSYNC` 必须关掉

上一轮同时打开了 bounce buffer 和 `CONFIG_LCD_RGB_RESTART_IN_VSYNC=y`，所以无法归因。
读完 IDF 源码后可以确定：**只有 bounce buffer 是需要的，另一个在反噬它。**

### 证据一：`RESTART_IN_VSYNC` 打开时会编译掉驱动自己的精确检测

`esp_lcd_panel_rgb.c:1272-1289` `lcd_rgb_panel_try_restart_transmission()`：

```c
#if CONFIG_LCD_RGB_RESTART_IN_VSYNC
    do_restart = true;                       // 每个 VBlank 无条件重启
#else
    if (panel->flags.need_restart) { ... }                        // 有请求才重启
    if (panel->bb_eof_count < panel->expect_eof_count) { ... }    // 欠载检测
#endif
```

`bb_eof_count < expect_eof_count`（expect = fb_size/bb_size = 48）**正是"这一帧 DMA 没搬完 48 块"的
精确判据** —— bounce 模式下天生的欠载检测。打开宏就把这个精确判据扔了，改成每秒无条件重启 39 次。

### 证据二：无条件重启自己就会造成位移（驱动原注释）

`esp_lcd_panel_rgb.c:1265`：
> Reset the GDMA channel every VBlank to stop permanent desyncs from happening.
> Note that this fix can lead to **single-frame desyncs** itself, as in: if this interrupt
> is late enough, the **display will shift** as the LCD controller already read out the
> first data bytes, and resetting DMA will re-send those.

"重发开头字节"= 整体右移 + 右缘绕回左边，**正是用户描述的残留症状**。

### 证据三：bounce buffer 正是让 VSYNC 中断变晚的那个原因

`esp_lcd_panel_rgb.c:1028-1052` `lcd_rgb_panel_fill_bounce_buffer()`，在 **GDMA EOF 中断**里：

```c
memcpy(buffer, &panel->fbs[panel->bb_fb_index][...], panel->bb_size);
```

48 块/帧，每帧 768000 B **PSRAM→DRAM 的 CPU memcpy**，39 fps ≈ 30 MB/s 的拷贝全在 ISR 上下文。
→ 它推迟 VSYNC 中断 → 而无条件重启一旦迟到就位移。**即该宏制造了自己要防的条件。**

### 推论（重要，纠正上一轮的乐观判断）

上一轮记忆写的"反弹填充是 CPU 拷贝…**不会退化成每帧 768KB 额外拷贝**"是错的：
bounce 填充本身就是**每帧 768KB 的整帧拷贝**。它没在 `draw_bitmap` 里再叠一次拷贝是真的，
但"每帧 768KB CPU 拷贝"这件事是真的发生了，代价是 30 MB/s 的 ISR 拷贝流量。
**所以 `system_info_log_tasks()` 报的 taskLVGL 13% 是地板不是真相** —— FreeRTOS 运行时长统计
**不把 ISR 时间归给任何任务**。

## 本轮改动

1. `sdkconfig.defaults`：`CONFIG_LCD_RGB_RESTART_IN_VSYNC=y` → `# ... is not set`，
   旁边写了完整推理（三条证据都带文件名+行号）。删 `sdkconfig` 重建生效。
2. `system_info.c`：日志 `(62.5 Hz ceiling)` 措辞是错的 —— `LV_DEF_REFR_PERIOD` 是**请求**不是上限，
   面板只有 39 Hz。改为打印"asks X Hz, panel answers Y Hz -> update rate is panel-bound"。
3. `theme.cpp`：顶部注释说"没有 CJK 字形、Reader 以后从存储挂子集字库"，
   与事实相反 —— 实际编译进了 `lv_font_source_han_sans_sc_16_cjk`（约 1.1 MB，
   是 1.24 MB 镜像里最大的一项），Reader/Notes/FileManager 都在用。已改正。

## 交互性能（回答"卡顿"）· 三条结论

1. **面板 39 Hz 是硬上限**（pclk 16 MHz / 820 / 500）。porches 已是官方最小值，
   唯一提速手段是抬高 pclk —— 而那会**加大** DMA 带宽压力，即当初位移的成因。不动。
2. **direct 模式下每次 flush 阻塞 LVGL 任务整整一帧**。`esp_lvgl_port_disp.c:748-756`
   无条件 `xSemaphoreTake(trans_sem, portMAX_DELAY)`，而 `trans_sem` 在 bb 模式下由
   `on_frame_buf_complete` 给 —— **每完成一整帧给一次**。
   → 改两个像素的按钮高亮也要等满 25.6 ms；输入轮询在同一任务同一 `lv_timer_handler()` 里，
   → 落在 flush 期间的触摸要等它出来才被看见。
3. 因此期望值是"交互时约 39 次/s，最坏 26~50 ms 点按延迟"。**低于 39/s 才说明面板以上真有瓶颈**。
   空闲实测 `RATE renders = 3/s`，正好是性能浮层的 300 ms 重绘节奏 → 探针语义正确。

## 方法论沉淀（值得进 skill）

- **两个修复同时上 = 无法归因**。位移这种"改了 A 也改了 B 然后好了"的场景，
  必须最后做一次**单变量回退**确认哪一个是必需的。本轮就是靠回退才发现宏在反噬。
- **ISR 里的 memcpy 不会被 FreeRTOS 运行时长统计捕捉**，"CPU 占比很低"不等于"不忙"。
  判断显示通路忙碌要看驱动里有没有 ISR 内的大块拷贝。
- 读官方源码注释比读 Kconfig help 值钱：`do_restart = true` 的副作用只写在**代码注释**里，
  Kconfig help 只说好处。

## 本轮改动（`main/platform/touch/touch_driver.c`）
1. 时序对齐官方：RST 低 **100 ms** → INT 拉低 → **100 ms** → RST 高 → **200 ms**
   （原来：INT 先低 2 ms → RST 低 10 ms → RST 高 → 等 100 ms）
2. INT 释放改为 `GPIO_MODE_INPUT` + **内部上拉**（GT911 的 INT 是开漏输出，无上拉即悬空）
3. 加**零副作用诊断**（`DIAG` 行，1 Hz）：GPIO4 电平 / `s_touch->data.points` /
   indev 的 press·pressing·release 计数 —— 三层一次分开

## 本轮读源码得到的关键机制
- **`esp_lvgl_port` 主循环只在 `LVGL_PORT_EVENT_TOUCH` 时才主动 `lv_indev_read()`**，
  该事件只由触摸中断回调置位。
- **但 TIMER 模式的 indev 仍有 LVGL 自带的 read_timer**（`lv_indev.c:133`，周期 =
  `LV_DEF_REFR_PERIOD`；`lv_indev_set_mode` **只在 EVENT 时 pause**）。`lv_timer_handler()`
  会跑到它 → 轮询模式下输入**应当**被读取。所以 `int_gpio_num = NC` 本身不会造成
  "输入永不读取"，这条路径成立。
- **`CONFIG_LV_USE_GESTURE` 未启用** → `lvgl_port_touchpad_read()` 里的手势分支不编译，
  排除"手势识别器改写 data->state"这一变量。
- GT911 的 `read_data`：读 `0x814E`，`bit7 == 0` 即判无触摸；读到坐标后**写 0 清除**。
  → **任何"直接读状态寄存器"的探针都会抢走 buffer-ready 位**，所以诊断必须被动。

## 方法论沉淀
- **"触摸不工作"要分层取证**：硬件层（INT 电平）/ 驱动层（`data.points`）/ LVGL 层
  （indev 事件）。被动观测三层，一次烧录即可定位，胜过按猜测改配置多烧一版。
- 对照官方例程**必须拿到 .h**：`EXAMPLE_PIN_NUM_TOUCH_INT = (-1)` 才是"官方走轮询"的
  证据；只看 .c 会误以为它配了中断。
