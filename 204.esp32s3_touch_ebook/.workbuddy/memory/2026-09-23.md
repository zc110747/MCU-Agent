## 2. SD 卡挂载失效（本次主要问题，可复现）

**现象**：同卡同固件，第 1 次启动挂载成功（`SA08G 7580 MB`），第 2/3 次启动失败，
**复位无法恢复**，用户在自己重启设备后也遇到同样问题。

**取证**（`serial_probe1.txt` / `/tmp/probe2.raw` / `/tmp/probe3.raw`）：

```
第2次: I (1342) sdspi_transaction: cmd=52, R1 response: command CRC error
       I (1386) sdspi_transaction: cmd=5,  R1 response: command not supported
       E (1389) sdmmc_common: sdmmc_init_ocr: send_op_cond (1) returned 0x102
第3次: I (...) sdspi_transaction: cmd=52, R1 response: command CRC error
       E (1365) vfs_fat_sdmmc: sdmmc_card_init failed (0x107)   # ESP_ERR_TIMEOUT
```

关键推理（已核对 IDF v6.1 源码，非猜测）：
- `cmd=52`=`SD_IO_RW_DIRECT`(R5)、`cmd=5`=`SD_IO_SEND_OP_COND`(R4)，**都是 SDIO 命令**
  → 走的是 `r1_sdio_response_to_err()`，它用 `ESP_LOGI`；而 R1 路径用 `ESP_LOGD`。
  **所以屏幕上只显示这两条 I 级日志，完整命令序列被 `CONFIG_LOG_MAXIMUM_LEVEL=3` 编译掉了**
  —— 这是判断"驱动走错分支"还是"卡片状态坏"的盲区。
- `sdmmc_init_ocr`（`components/sdmmc/sdmmc_common.c:26`）在 SPI 模式下只发 ACMD41
  (`sdmmc_send_cmd_send_op_cond`)，0x102/0x107 就是这一步失败。
- `SDSPI_HOST_DEFAULT()` 确实带 `SDMMC_HOST_FLAG_SPI`，所以 `host_is_spi()` 为真，
  不是"忘了设 flag"这种低级错误。

**当前怀疑（未证实，机制层面）**：本项目 CS 由 CH422G EXIO4 驱动，
`sd_card.c` 用 `SDSPI_SLOT_NO_CS` 告诉 SPI-SD 驱动"没有 CS 引脚"，
于是**从 mount 开始 CS 一直被拉低、全程不复位**，同时
**没有任何地方产生 SD 规范要求的 ≥74 个"CS 高电平"空闲时钟**。
若复位时卡片正处于半条命令/写操作中，它的状态机就卡住，普通复位（CS 仍为低）清不掉，
只有**卡片自身掉电**才能复位。

**已做的加固实验（未完成）**：
- `sdkconfig.defaults` 末尾临时加 `CONFIG_LOG_MAXIMUM_LEVEL_DEBUG=y`（**已删除 `sdkconfig` 重新播种，
  新 sdkconfig 已是 `CONFIG_LOG_MAXIMUM_LEVEL=4`**；`LOG_DEFAULT_LEVEL` 仍为 INFO，
  由探针运行时对 sdspi/sdmmc 四个 tag 单独开 DEBUG，避免被 LVGL 日志淹没）。
- 探针 `dev_probe_fs()` 里加"重复 mount 3 次 + 200ms 间隔"，用来回答：
  **失败是粘住的还是重试能好**。
- 用户取消了这次构建，**尚未验证**。

**给用户的即时建议**：整机断电重上电（不是复位键），卡片冷启动后才能清状态；
同时可拔插一次 SD 卡排除接触。

## 3. 探针 v2 的修正（重要教训：探针自己不能吃栈）

v1 崩溃 backtrace `CORRUPTED`、`PC=0x200`、`A0=0x200`、`A9=0xb33fffff`(FreeRTOS 临界区哨兵)
→ 符合"栈被打穿后读到野返回地址"。

v1 在**栈上**放了 `DirEntry f[32]`(4352 B) + `DirEntry tmp[8]`(1088 B)，
而 **main 任务栈只有 `CONFIG_ESP_MAIN_TASK_STACK_SIZE=8192`**。
v2 全部改 `static`（BSS）后：`STACK free=6468 B` 全程不再下降 → 栈压力解除。

`sizeof(services::DirEntry)=136`，所以 `entries_[64]` = **8704 B**：
`PhotosPage::entries_` / `ReaderPage::entries_` 都是这个尺寸。页面对象由
`AppManager::instantiate()` 用 `new (std::nothrow)` 从堆上建（`app_manager.cpp:209-223`），
所以目前安全 —— **但绝不能把 Page 对象放到栈上**。

v2 新增：栈水位 (`uxTaskGetStackHighWaterMark`) + 手工解析 JPEG SOF/PNG IHDR/BMP DIB
拿**真实像素尺寸**（不依赖被怀疑的解码器），并打印 ARGB 解码体积估算。

## 7. 结论与修复（已真机验证）

### 7.1 SD 挂载 —— 已修复

根因不是卡片坏，是**缺 SD 规范要求的唤醒序列**（第 2 节那个"当前怀疑"**已被证据证实**）。

修复 `main/platform/storage/sd_card.c`：mount 前先
`io_expander_sd_cs(true)`（CS 拉高）→ 用**临时无 CS 的 SPI device** 发
**80 个 400 kHz 空闲时钟**（`spi_bus_add_device` + `spi_device_polling_transmit`，
`spics_io_num = GPIO_NUM_NC`）→ `io_expander_sd_cs(false)` → mount；
整套失败时重来，最多 3 次。

验证证据（`serial_fix1.txt`）：

```
I (1386) sdspi_transaction: cmd=5, R1 response: command not supported
I (1432) sd: mounted at /sd  SA08G  7580 MB
I (1432) main: SD card    : mounted at /sd
```

**第 1 次尝试即成功**（日志里没有 "mount attempt 2/3 failed"）→ **归因干净**：
是唤醒序列修好的，重试逻辑**未被触发**（留作保险，不是搭便车）。

### 7.2 开机多次重启 —— 已消除

根因是**我加的临时探针**，不是业务代码：`serial_probe1.txt` 里两次
`Guru Meditation (InstrFetchProhibited)` + `rst:0xc (RTC_SW_CPU_RST)` =
探针在启动序列里跑 → 崩 → 重启 → 再崩，就是用户看到的"开机后页面多次重启"。

还原探针（`git checkout --` 三个文件 + 删 `dev_probe.*` + 删 `sdkconfig` 重新播种）后，
20 秒捕获里只有 1 次 `rst:0x15 (USB_UART_CHIP_RESET)`（脚本自己发的）→ **无 panic、无重启循环**。

`request_restart()` 只在 `settings_page.cpp:371` 被调用 → 业务侧本来就没有开机重启路径，
佐证重启循环 100% 来自探针。

**教训（写进约定）**：诊断代码必须能在**最坏情况下全身而退**。探针崩溃会变成
用户看到的"设备在自己重启"，还会污染它正要测量的硬件状态（见 7.1 的粘卡）。

## 9. IDF 源码事实（可复用，非猜测）

- `sdmmc_init.c:79-88`：`CMD52(sdmmc_io_reset)` / `CMD5(sdmmc_init_io)` 是否发送由
  `CONFIG_SD_ENABLE_SDIO_SUPPORT=y` 决定，**SPI 模式也会发**（`io_supported` 不排除 SPI）。
  普通 SD 卡必然回 "command not supported"，**无害**，之后才走 ACMD41。
  → 看到 `cmd=52`/`cmd=5` **不能**推断"驱动走错分支"（第 2 节的推理到此修正）。
- `sdmmc_common.c:26 sdmmc_init_ocr()`：SPI 模式只发 ACMD41；
  `0x102`(ESP_ERR_INVALID_ARG) / `0x107`(ESP_ERR_TIMEOUT) 都是这一步的失败码。
- `SDSPI_HOST_DEFAULT()` 带 `SDMMC_HOST_FLAG_SPI`（`sdspi_host.h:42`）。
- `esp_vfs_fat_sdspi_mount()` 失败走 `goto cleanup` → `call_host_deinit()` + `free(card)`，
  **slot 清理干净，可安全重试**（`vfs_fat_sdmmc.c`）。
- 编译期坑：`spi_device_polling_transmit()` 第二参数**非 const**，
  写成 `const spi_transaction_t` 会被 `-Werror=discarded-qualifiers` 拦下。

## 12. Photos 崩溃的根因取证（方法可复用）

症状：每次开机进 Photos 就重启。**堆从来不是问题**（死时 PSRAM 还有 5.6 MB 空闲）。

- `***ERROR*** A stack overflow in task main has been detected.`
- `addr2line` 把回溯解到 `vApplicationStackOverflowHook` —— **这是检测器，不是肇事者**，
  照它去改会白费一轮。
- 正解是 `objdump -d` 量栈帧：`lv_tjpgd.c.obj:decoder_info` 有 `entry a1, 0x10b0` = **4272 B**，
  来自 `lv_tjpgd.c:110 uint8_t workb[TJPGD_WORKBUFF_SIZE]`（4096）+ `JDEC jd`（176）。
  它在**渲染**路径上（`lv_image_decoder_open` 读文件头就进），叠在 ~5.3 KB 控件树递归上，
  实测峰值 **10156 B** > 8192 B 栈。
- 上游自身不一致：`decoder_open` 改用堆分配，`decoder_info` 还在用栈。
- **`managed_components/` 不要打补丁**（gitignore + 会被组件管理器重生成）。

## 13. SD 字库（F3）关键事实

- flash 内嵌 `lv_font_source_han_sans_sc_16_cjk` 是**手工挑的 demo 子集**（1432 码点），
  生成头里的 `--symbols` 就是那份清单 —— 这才是「部分文字乱码」的真因，不是转码问题。
- 正文样本（`doc/prompter-step1.md`，530 个不同汉字）覆盖率：**283 (53.4%) → 524 (98.9%)**；
  新可渲染码点 **20514** 个；剩下 6 个是 emoji（两套字体都没有）。
- 复合字体（卡字库 + `fallback` 到内嵌）是**超集**，前提是 `fallback` 链挂着 —— 它同时承担
  ASCII、**`LV_SYMBOL_*` 所在的私用区**（卡字库 PUA 单元数 = 0，《U+F001..U+F8A2》60 个只在内嵌里）
  以及 cp936 未定义的槽位。`lv_font.c:104-122` 是 `while(f){... f=f->fallback;}`，
  `lv_font.c:51/64/87` 按 `dsc->resolved_font` 取位图 —— 机制已核对过源码。
- **两套索引公式别混**：HZK 190 码位/区（0x7F 不是尾字节），`gbk_table` 191。差 1 就整体错位。
- `dsc->stride = 0` 是安全的：`lv_draw_label.c:603` 用 `box_w/box_h/LV_STRIDE_AUTO` 建缓冲，
  消费侧读 `draw_buf->header.stride`（`lv_draw_sw_letter.c:180`），**从不看 `dsc->stride`**。
- 交付形态：反查表是**运行期从 `gbk_table` 导出**的 64 KiB 平表（PSRAM），
  不是再生成一份文件 —— 一份真值而不是两份可能不一致的。
- **布局不是「零变化」，差 2 个字符**：内嵌子集把 `、` 栅格化成 141/16=8.81 px、
  `（` 成 258/16=16.125 px；本字库统一 16 px，所以 `、` 加宽 7.2 px 可能让含它的行提前折行。
  其余 1275 个 CJK 前进宽度都是 16 px，断行/分页不变。`tools/verify_sd_font.py` 把这两个钉住。

### 三个只有烧进去才看得见的坑（都已修 + 已固化成断言）

1. **本机主动断开被记成失败 ⇒ 重试账目错位。**
   `WIFI_REASON_ASSOC_LEAVE`(8) 与 `STA_LEAVING`(36) **只可能**由我们自己的
   `esp_wifi_disconnect()` 产生，而三个调用点把它当**通往链路的一步**：
   `net_wifi_connect()` 重配前、`net_scan_start()` 拿射频前、Disconnect 按钮。
   只判 `s_want_connected` 会漏掉前两个（意图仍是「想要链路」）→ 扫描自己的断开
   吃掉重试格 1 → 日志只有 `attempt 2/3` 没有 `1/3`，计数器说 3 次实际只发 2 次。
   **教训：意图与「这份报告是不是故障」是两个问题，第二个只能从 reason 答。**
2. **`esp_timer_start_once()` 对已武装的定时器返回 `ESP_ERR_INVALID_STATE` 且不重启。**
   症状：两次失败只隔 184 ms，第二次武装静默失败 —— 预算吃掉一格却没买到尝试。
   修：`s_retry_pending` 合并同一窗口内的重复报告（保险，非主路径）。
3. **开机自连：配置不跨复位，`esp_wifi_connect()` 空手而归。**
   `WIFI_STORAGE_RAM` + 驱动 NVS 关闭 ⇒ 配置只活在 RAM。`WIFI_EVENT_STA_START`
   分支只调 `esp_wifi_connect()`、**没调 `esp_wifi_set_config()`** → 返回
   `ESP_ERR_WIFI_SSID`、不产生事件、返回值还被丢弃 → 面板永远 connecting。
   实测 18 s 内无 `wifi:state: init -> auth`；同一凭据走 `apply_and_connect()` 1.24 s 进 auth。
   **这条只在探针移出、看纯净固件启动日志时才暴露** —— 有探针时是探针自己把配置写进去的。
   **教训：诊断探针会替被测代码完成前置动作，从而掩盖缺陷。移出探针后必须重抓一次。**

### 关键数字（实测）

- 内部 SRAM 代价 **75 172 B**（`213951 -> 138779`）；开机结束 `heap int=121003 / largest=79872`
  （加 WiFi 前 247067 / 204800）。PSRAM 侧 `SPIRAM_TRY_ALLOCATE_WIFI_LWIP` 接走约 660 KB 流量缓冲。
- **分配顺序是面板的保证**：`display_init()` L94 早于 `net_init()` L126，面板先拿内存。
  把 `net_init()` 提前 = 改动面板的内存保证，不只是改启动顺序。
- 真机：`wifi:connected with test, aid = 3, channel 11` → `net: connected, ip 192.168.3.6, rssi -30 dBm`；
  失败路径 `reason 201` → `1/3`(+5000 ms) → `2/3` → `3/3` → `giving up after 3 retries`；
  Forget 后 9 s 无重试、`has_creds=0`。

### `tools/verify_wifi.py`（新增，28/28）

读抓回的日志重放状态机，**先从源码读 `kMaxRetries`/`kRetryDelayMs`** 再断言（常量改了脚本会失败
而不是跟着改）。解析时间戳 → 能断言「每次重试都等满间隔」，这条正是定时器没重启时会 FAIL 的。

### 17.4 PCF85063A 年寄存器硬上限 = 2000–2099（可复用的平台事实）

→ Settings 的 2000–2100 是 UI 展示范围，落盘上限仍是 2099，这点 UI 文案/注释要说清。

屏蔽 12/24 位，导致读回时间与设置值有 ~7 h 偏差。属平台预存怪癖，用户未要求修 RTC 驱动，
保持原状。

## 18. Clock 秒不递增 → 软件时钟兜底（本回合，commit `0fb1bfc`）

用户纠正：秒**能显示但冻结**（之前说"不显示"是错的）。真机采样 6 次 `sec=00 min=14 hr=03→08`
→ 秒冻结、小时每真实秒 +1。逐字节读写验证后结论：**PCF85063A 秒计数器硬件损坏**
（SECONDS 永远 0x00、HOURS 每真实秒 +1、MINUTES 正常），任何 I²C 模式都救不了坏硅。

修复（`clock_service.cpp`）：时间改由 **ESP-IDF 系统时钟**（`time()`/`settimeofday`）作权威走时源，
`clock_init()` 从 RTC 播种一次、`clock_set()` 同步写回 RTC 持久层；`clock_now()` 读系统时钟
（不再读冻坏的 RTC）。验证：临时 boot 采样器（已删）打印 `sec=01→06` 间隔 ~1000 ms → 1 Hz 递增确认。
零警告构建（exit 0 / 0 warn / 0 err）、烧录 COM14、boot 干净（无 PROBE / 无 VERIFY）。

**PCF85063A 两个硬件怪异（已固化进 `pcf85063.c` 注释）：**
1. 不支持自增块读/写 → 逐寄存器单字节事务（`get`/`set` 已改）。
2. 秒计数器损坏 → 系统时钟兜底；RTC 仅持久层。
附带：年份寄存器写入也不持久（读回 0x06=2006 而非 0x26=2026），该芯片日期也不可靠；
SetTime 运行时能纠正屏幕时间，复位可能恢复 RTC 存的旧日期（非阻塞，用户未要求深修）。

探针清理：删 `pcf85063.c` / `clock_page.cpp` / `main.cpp` 全部 TEMP-PROBE / VERIFY 代码，
交付固件无探针。
