### 修复：最终链接失败（undefined reference to tud_descriptor_*）
- 根因：ESP-IDF 把组件编译成 `.a`，链接器只拉取能解析未定义符号的成员。`usb_device` 组件因
  REQUIRES tinyusb 而排在 tinyusb 之前被扫描，`usb_descriptors.c.obj`（提供 tinyusb 要求的
  `tud_descriptor_*` 回调）被丢弃 → undefined reference。同时强定义的 `__weak` 覆盖也会因此被丢，
  让 tinyusb 弱桩静默胜出（HID 收不到报告等隐患）。
- 用户指令：**不要编译成 .a 形式、最终一起全部链接**，避免 `__weak` 误链。ESP-IDF 组件天生是 .a，
  结构性正解是**最终链接用 `--whole-archive` 包裹自定义组件归档**，让所有目标文件无条件纳入。
- 实现：在 `main/CMakeLists.txt` 用 `idf_component_get_property` + `target_link_libraries`
  `-Wl,--whole-archive "$<TARGET_FILE:lib>" -Wl,--no-whole-archive"` 包裹
  usb_device/cmsis_dap/debug_engine/swd/target 五个组件（从 main 引用，避免组件自链接）。
- 移除了之前在 `usb_device.c` 加的 dummy-reference 补丁（不再需要）。

## CMSIS-DAP v1 主机识别 / 驱动关键结论（已验证分析）

- 设备插上被"当成 USB HID 而非 CMSIS-DAP"是**正常**的：v1 就是 HID 类设备，设备管理器
  本就在"人体学输入设备"下。识别靠产品字符串含 "CMSIS-DAP" + HID Usage Page=0xFF00/usage=0x01。
  已核对固件 `usb_descriptors.c`：HID Report Descriptor 用 `TUD_HID_REPORT_DESC_GENERIC_INOUT`
  （usage page 0xFF00，符合）；产品/接口字符串均含 "CMSIS-DAP"；端点方向经查
  `TUD_HID_INOUT_DESCRIPTOR(_itfnum,_stridx,_boot,_rlen,_epout,_epin,...)` 宏定义确认
  OUT=0x01 / IN=0x81 正确，非 bug。`dap_info` 与命令分发覆盖 Keil 必需全部 DAP 命令。
- **WinUSB 陷阱（用户已踩）**：用户用 Zadig 把原生 USB 强装 WinUSB 后，Windows 能读出
  产品名（描述符正常），但 Keil 的 CMSIS-DAP 走 HIDAPI 必须 `hidusb.sys` → WinUSB 绑死后
  HID 通道打不开，Keil 看不到设备。
  - **正解**：v1 HID 设备驱动必须是系统自带 `hidusb.sys`（插上自动绑定），**禁止** WinUSB。
  - 还原：设备管理器卸载设备并勾"删除驱动"→ 重插 → 系统自动装回 hidusb。
  - WinUSB 仅适用于 CMSIS-DAP **v2**（Bulk 传输，需改固件：vendor class + BOS/OS 描述符 + bulk 端点）。
- 两个 USB 口要分清：原生 USB(GPIO19/20)=CMSIS-DAP HID=Keil 用的口；CH340(GPIO43/44, COM21)
  = 仅 UART 日志/烧录串口，不是调试接口。
- 已将上述写入 `doc/useage.md` 第 7 节（驱动黄金法则 / 还原步骤 / Keil 用法 / 双 USB 口区分）。
- **用户系统 = Windows 10**。Win10 上还原 WinUSB 的关键：卸载设备时务必勾"尝试删除此设备的驱动程序"，
  否则重插会因驱动排名再次自动绑回 WinUSB。也可用 Zadig 把目标设备下拉改回 "HID-compliant device"。
  已补充 Win10 步骤到 `doc/useage.md` 7.2 / 7.6（含按连接列出设备、pyOCD/OpenOCD 交叉验证、硬件 ID 排查）。

### 固件侧根因修复：OpenOCD `CMD_INFO failed`（已完成，参考 007 项目校正）
- 用户跑 `openocd -f interface/cmsis-dap.cfg -f target/stm32h7x.cfg` 报 `Error: CMSIS-DAP command CMD_INFO failed.`
  驱动已正确（hidusb.sys），故问题在**固件 CMSIS-DAP 协议层**，不是驱动。
- **权威依据 = 参考项目 `007.stm32h743_cmsis_dap`**（完整、已测通过的 STM32H7 实现，直接调用 ARM 官方
  `DAP.c`/`DAP.h` v2.0.0）。核对其 `bsp/DAP_config.h`、`app/main.c`、`third_party/CMSIS-DAP/DAP.h` 后
  确认：**ARM 的 InfoType 键是 1-based**（DAP_ID_VENDOR=1, DAP_ID_PRODUCT=2, DAP_ID_SER_NUM=3,
  DAP_ID_FW_VER=4, DAP_ID_CAPABILITIES=0xF0, DAP_ID_PACKET_COUNT=0xFE, DAP_ID_PACKET_SIZE=0xFF）；
  **`DAP_Info` 响应格式 = `[cmd, length, data...]`**，即 `response[1]` = **payload 长度**（OpenOCD/Keil 解析它），
  数据从 `response[2]` 起。
- **此前某次"修复"是错误的**（把 `response[1]` 当 InfoType 回显、将 dap_info case 改成 0x00 起始）。
  那是错误的理解。本次以 007 项目为规范源**重新校正**：
  1. `dap_info()` switch 改为 **1-based keys**（case 1/2/3/4/0xF0/0xFF/0xFE），与 ARM DAP.h 完全对齐。
  2. `ID_DAP_Info` 分支：`response[1] = (uint8_t)num`（= 长度），返回 `(2<<16)+2+num`，数据写入 `response+2`。
     这才是 ARM 规范要求的格式，OpenOCD 才会认可。
  3. `dap_task` 取 `exec_ret & 0xFFFF`（低16位=响应长度）传给 `usb_device_send_response`，不再整段当 len。
  4. 顺手：响应缓冲 `memset` 清零（Info 字符串隐式 null 终止）；serial `snprintf` size = `DAP_PACKET_SIZE-2`；
     FW 版本 `sizeof-1` 去掉自带 '\0'；capabilities=SWD(0x01)|atomic(0x10)；packet count=1（HID v1 单缓冲）。
- 加了 COM21（UART0）调试日志：HID OUT 回调边界（`HID OUT cmd=... len=...`）、命令分发（`DAP cmd id=...`）、
  `DAP_Info id=... len=...`。可肉眼观察 OpenOCD 的完整命令流。
- 修复后 `build` 零警告零错误（exit 0），已 `flash -p COM21 -b 460800` 烧录成功（Hash verified + Hard reset Done）。
- 关键规范点：CMSIS-DAP v1 HID `DAP_Info` 响应 = `[cmd, length, data...]`；字符串类型靠缓冲零填充隐式
  null 终止；数值类型（0xF0 能力位/0xFF 包大小/0xFE 包计数）紧随 byte2。
- 请用户重跑 OpenOCD 确认：预期**不再**报 CMD_INFO failed，应进入连接目标流程（需外 MCU 接好 SWD 三线）。

## 22:52 续 — SWD 通 / JTAG 不通 实测诊断（用户恢复供电后）

### 实测结论（PC 直发 DAP 命令，探针在线）
- 目标恢复供电后：TDO 被目标**主动拉低**（SWJ_Pins bit3=0），说明 TDO 飞线 / 目标上电均正常。
- `dap_connect(SWD)` 内部 `swd_jtag_to_swd()` 生效：SWD DPIDR ack=OK → **SWD 路径真通**（与用户反馈一致）。
- JTAG `DAP_JTAG_IDCODE` 始终回 `FF`（TDO 浮空 / 无 TAP 响应）。
- 手动 `DAP_SWJ_Sequence(0x12)` 发 SWD→JTAG 魔数 0xE73E 后，SWD 仍存活（DPIDR 仍 OK）→ 切换未生效
  （注：实验脚本曾把 COUNT 发成字节数，后改位数 118 重测仍无效；但固件 J2S 路径已证明 bit-bang 引擎正常，
   故"未生效"更可能是 DP 锁在 SWD 模式后需要别的触发，或 0x12 时序细节）。

### 已确认的根因（代码层）
1. **JTAG connect 路径不切回 JTAG 模式**：固件只有 `swd_jtag_to_swd()`（swd_connect 调用），
   **完全没有 `swd_swd_to_jtag()`**，且 `dap_connect(JTAG)` 不发 SWD→JTAG 切换序列。
   SWD 会话把 SWJ-DP 锁进 SWD 模式后，JTAG TAP 被禁用 → 读 IDCODE 永远 FF。这精确解释"SWD 成功、JTAG 反而死"。
2. **SWJ_Pins 位映射错**：固件把 nTRST 放 bit5、nRESET 放 bit7；CMSIS-DAP 规范是 nTRST=bit4(0x10)、
   nRESET=bit5(0x20)。OpenOCD 的 SRST 请求(bit5)会被固件误当作 nTRST 驱动，复位行为错乱。

### SWD 读数据相位已核实正常
`swd_transfer` RnW 读路径：line22 释放 SWDIO → turnaround → 32 位读数 → 重新使能输出，逻辑与 ARM SW_DP.c 一致，
故 SWD 读是通的。实验里 DPIDR 回 0 属 PC 端 0xA5 包细节/时序问题，非固件读引擎缺陷（待 OpenOCD SWD 实测 DPIDR=0x6BA00477 复核）。
