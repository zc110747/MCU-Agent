## 第四版：PRINT_LOG 日志系统替换全部 printf（参考 101 项目 log.c/bsp_uart.c）

### 需求
用 `101.stm32f429_net` 的 `app/log.c/.h` + `bsp/bsp_uart.c/.h` 替换系统中的所有
printf 打印，用 `PRINT_LOG` 做可控实现。

### 实现
- 新增 `app/log.c/.h`：`printf_log()` / `vprintf_log()` / `PRINT_LOG()` 宏 +
  `PRINT_LOG_ENABLE` 全局开关。192 B 栈缓冲 + `vsnprintf` → `uart_write(带显式长度)`。
- `bsp/bsp_uart.c` 升级为 101 语义：
  - 调度器未运行 → `HAL_UART_Transmit()` 阻塞轮询（启动横幅不丢字节）
  - 调度器已运行 → 互斥量 + 临界区入环，由 TXE ISR 排空
  - 新增 `uart_flush()`（带 guard 计数，绝不死等）
- `app/` + `bsp/` 共 12 文件 79 处 `printf(` → `PRINT_LOG(`；`snprintf` 一律保留。
  批量替换用 `sed -i 's/\bprintf(/PRINT_LOG(/g'`（`\b` 天然跳过 snprintf/vsnprintf）。
- CMake：`option(ENABLE_PRINT_LOG ... ON)` → `-DPRINT_LOG_ENABLE=0|1`。

### ★ 两个必须记住的工程约束
1. **`BSP_UART_Init()` 在 SDRAM / `vPortDefineHeapRegions()` 之前调用**
   （main.c 里先起串口才能打启动横幅）。所以 TX 互斥量**绝不能**像 101 那样在
   init 里创建 —— 改成调度器运行后**惰性创建**（`tx_mutex_get()`，临界区保护）。
2. **U 盘内容 dump 不能走 `PRINT_LOG`**：它是二进制原文、可能不含 NUL，
   直接当格式串遇到文件里的 `%s` 会崩。保持 `uart_write()` 直连，
   但用 `#if PRINT_LOG_ENABLE` 整段包住（关日志时直接 return，连盘都不读）。

### 产物（三种配置，全部零警告）

|---|---|---|
| Release 日志开 | 298,120 B (28.43%) | 30,272 B (15.40%) |
| Debug 日志开 | 259,236 B (24.72%) | 30,264 B (15.39%) |
| Release 日志**关** | **291,960 B (27.84%)** | 30,272 B (15.40%) |

日志关掉省 6,160 B。相比第三版（302,244 B）反而**小了 4.1 KB** ——
`PRINT_LOG` 走 `vsnprintf` + 定长 `uart_write`，绕开 newlib `printf` 的完整格式化栈。

### 验收：COM5 挂了 → 改用 SWD 读内存取证（PASS 6/6）
验证时 **COM5 (CH340 @ LOCATION=1-8) 报 `PermissionError(13) / code 31`**，
COM4 是另一个 CH340 不是本板（抓 0 字节）。串口侧完全不可用。

**替代方案（已封装成 `tools/verify_serial/verify_log_switch.py`）**：
日志关掉后固件不该往 TX 环形缓冲放任何一个字节，所以直接 halt 后读
`bsp_uart.c` 的静态变量即可判定：
- `g_tx_head`（uint16）TX 环写指针
- `g_tx_tail`（uint16）TX 环读指针
- `g_tx_busy`（uint8）发送器忙标志
- `g_usb_state`（全局）确认系统完整启动到 USB_MOUNTED=4

实测：
```
PRINT_LOG 开 : g_tx_head=0x0350  g_tx_tail=0x0350  g_tx_busy=0  g_usb_state=4
PRINT_LOG 关 : g_tx_head=0x0000  g_tx_tail=0x0000  g_tx_busy=0  g_usb_state=4
```
→ 日志关时**一个字节都没进环**，且系统照常启动到 USB 挂载。

### 踩坑
- **OpenOCD `mdw` 读非对齐地址会报 `Failed to read memory`**：
  `g_tx_busy`(uint8 @0x...51) + `g_tx_tail`(uint16 @0x...52) + `g_tx_head`(uint16 @0x...54)
  三个变量紧挨着、地址不是 4 字节对齐。必须按 4 字节对齐整字读，再在 Python 里切字节。
- **枚举读出来是 `0x03200004`**：`g_usb_state` 是 `usb_state_t` 枚举，
  取 `& 0xFF` 即可（Cortex-M 小端，LSB 在前，无论编译器把枚举做成 1 还是 4 字节都对）。
- **残留 openocd 进程会让 ST-Link 报 `libusb_open() failed with LIBUSB_ERROR_ACCESS`**：
  `taskkill` 清掉后即恢复。
- log 关闭构建时 `dump_file()` 里 6 个局部变量未使用会报警告 →
  把变量声明一起挪进 `#else` 分支即可。

# 第五轮：修复「FreeRTOS 起来后 I2C2 读 AP3216/MPU9250 失败」

## 症状（用户报）
系统未启动时 I2C 正常；FreeRTOS 起来后 `[SENS ] AP3216C/MPU9250 read FAILED (rc=-1)`，
且**之后每次都失败**。日志同时有 `irq=93014`、触摸坐标卡在 `raw=(436,771)` 不变。

## ★ 根因链（决定性证据是"时序"）
传感器 init 在**触摸 EXTI 使能之前**成功、之后失败 → 指向触摸中断。
加 IRQ 速率看门狗后一击命中：`T_PEN interrupt storm 46925/s`。

1. **PH7 (T_PEN) 中断风暴**：原为 `GPIO_NOPULL` 浮空输入，且紧邻 PH6（位绑定 SCL
   165 kHz）→ 容性串扰。正点原子用 NOPULL 是因为它只轮询且模块自带上拉；
   **我们用 EXTI 就必须上拉**。
2. `HAL_I2C_Mem_Read/Write` 是**轮询式**传输，CPU 必须留在循环里逐字节搬运；
   触摸任务 idle+4 > 传感器任务 idle+1 → 传输被位绑定扫描抢占。
3. 抢占 → HAL 10 ms 超时 → 从机仍拉住 SDA、I2C2 锁在 BUSY。
4. 旧代码失败后**只退避重试、从不调 `BSP_I2C_Recover()`** → **总线永久卡死**。
   这就是"一失败就永远失败"的直接原因（该函数本来就是为这个场景写的）。

## 三层防护（缺一不可）
| 层 | 措施 |
|---|---|
| 源头 | PH7 改 `GPIO_PULLUP`（仅地址锁存那一瞬用 NOPULL） |
| 源头 | 位绑定 I2C 事务期间屏蔽 EXTI line 7 |
| 源头 | **ISR 内立即屏蔽 line 7**；任务侧消抖 5 ms 后 `bsp_touch_irq_rearm()` 重新武装 |
| 隔离 | 传感器读取用 `vTaskSuspendAll()`/`xTaskResumeAll()` 包成原子操作（中断仍开） |
| 容错 | I2C 超时 10ms→50ms；失败先 `BSP_I2C_Recover()` 再立即重试一次 |
| 兜底 | `TOUCH_MAX_POLLS`(200×15ms=3s) 上限，幻接触不能永久占用任务 |
| 自诊断 | IRQ 速率看门狗 >1000/s 打 WARNING |

## 顺带查出两个真实缺陷
1. **磁力计时序**：`SMPLRT_DIV=7` → 125 Hz（周期 8 ms），而 `ak8963_read()` 只等 2 ms
   → `EXT_SENS_DATA` 还没搬完。已改为 `MPU_SLAVE_SETTLE_MS 20`（≥2 个采样周期）。
2. **AK8963 根本不存在**：加 `AK8963_WIA`(0x00) 检测后实测 **WIA=0x00** ——
   这颗"MPU9250"没有可用磁力计。旧代码把全零当"读取成功"上报，属于**谎报**。
   现在 init 返回 -3、页面显示「磁场  AK8963 未装配」。

## 验收（全部真机）
- `verify_sensors.py`（新，SWD 直读 `s_data`）：**7/7 PASS**
  `errors=0`、`samples=38`、`|a|=1.00 g`（板子平放重力全在 Z）、ALS 随光照 0→4→10 lux
- `verify_touch_irq.py` 7/7、`verify_boot_flow.py` 17/17，均无退化
- 三配置零警告：Release 299,344 B / Debug 259,996 B / Release(log off) 292,936 B

## ★ 方法论沉淀
- **"没报错" ≠ "有数据"**：错误日志还是限流的，正向验证必须直接读目标内存里的
  数据结构（`arm-none-eabi-nm` 取址 + OpenOCD `mdw`）。
- **给中断加"速率看门狗"**：一条 WARNING 就能把"中断风暴"从猜测变成实测数字，
  是所有 EXTI/GPIO 中断类问题最划算的诊断投入。
- **噪声中断的正解是 ISR 内屏蔽 + 任务侧延时重新武装**，不是 ISR 里做软件滤波；
  前者把 ISR 速率压到 ~20 Hz，后者只是自欺欺人。
- **轮询式 HAL 传输（I2C/SPI 无 DMA）在高优先级任务忙等时会被抢占**，
  要么加大 timeout，要么用 `vTaskSuspendAll()` 保护成原子操作。
