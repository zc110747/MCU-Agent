## 2026-08-14（续）— 相机在真机（#002 板）实测 + 修复

### 关键澄清
- **COM19(ST-Link VCP) 与 COM4(USB CDC) 是同一块带 OV5640 的相机板**（#002 项目在其上验证正常）。此前 `ov5640 init failed` 不是「无传感器」，而是 #008 端口缺陷。

### 与 #002 对齐的修复（#34，全部已落地）
1. **I2C4 时序**：`hi2c4.Init.Timing` 由 `0x20A09DEB`(#005 值) → `0xF0421E25U`(#002 验证值)。两项目 D3PCLK1 均 = 120MHz，故同一时序值产生相同 SCL。
2. **I2C4 上拉**：PF14/PF15 由 `GPIO_NOPULL` → `GPIO_PULLUP`（#002 用 PULLUP）。
3. **DCMI DMA**：`DMA2_Stream7`+`MemBurst SINGLE`+优先级0 → `DMA2_Stream1`+`MemBurst INC4`+`VERY_HIGH`（#002 验证配置）；同步更新 `stm32h7xx_it.c` 的 `DMA2_Stream1_IRQHandler`、`main.c` 的 `MX_DMA_Init`（Stream1 中断使能/优先级5）、`MspDeInit` 关 Stream1 IRQ。
4. **AF 固件下载改为非致命**（根因）：`dcmi_ov5640_download_firmware()`（OV5640 AF MCU blob）此前失败即 `return RT_FAIL` 导致整个 init 失败。该 blob 在 #002 板的 OV5640 模组上不被接受；但 AF 固件对 RGB565 流媒体非必需（#002 从不下载它）。改为失败仅打印 `[CAM ] warning: AF firmware download failed (non-fatal)` 并继续。

## 2026-08-14（再续8）— 图片查看器「内存不足」修复（改用共享内存池）

### 需求（用户）
- 图片查看器显示「内存不足，无法打开」；要求改用此前已启用的 **共享内存池**（`sram_pool`）。

### 根因（定量分析）
- `bsp/jpeg_enc.c` 编码器与 `app/img_decode.c` 解码器是两回事。查看器走 `img_decode.c` 的 `decode_jpeg()`，用 ChaN 的 TJpgDec（`third_party/tjpgd`）。
- `third_party/tjpgd/tjpgdcnf.h` 设 **`JD_FASTDECODE = 2`**，其最坏需求 = `3500 + 6144 = 9644` 字节（6144 是 2 张 AC + 2 张 DC 哈夫曼快速查表 LUT，JD_FASTDECODE=2 专用）。
- 但 `img_decode.c` 只给了**静态** `static uint8_t s_pool[8192]`（8KB）——**小于解码器自身最坏需求 9644**。于是 `jd_prepare`/`jd_decomp` 返回 `JDR_MEM1`/`JDR_MEM2` → 文本映射为「内存不足」。
- 本机自己 `cap` 截的图是 **4:4:4 / 3 分量 JPEG**（4 张哈夫曼表），正好把 6KB LUT 用满 → **连自己截的图都打不开**，确证此 bug。

### 改动
- `app/img_decode.c`：
  - 删除静态 `s_pool[8192]` + `JPEG_POOL_SZ`；改 `#define IMG_JPEG_POOL (32u*1024u)`（32KB，给最坏需求 3 倍余量，连多表异常 JPEG 也够）。
  - `decode_jpeg()` 在解码前从 `sram_pool` 取工作区：**先 RAM_D2、失败退 DTCM**（`sram_alloc(region, IMG_JPEG_POOL, 4)`），所有出口（`goto done`）统一 `sram_free(region, pool)` 释放。图片查看器页与 NES 页互斥，查看时 RAM_D2 有 ~286KB 空闲，故稳取 D2。
  - 加 `#include "sram_pool.h"`。
  - BMP 路径不受影响（`s_line[8192]` 静态仍在）。
- `app/app_cmd.c`：为调试「X 打不开」新增**无 UI 的头端命令** `img decode <path>`（直接调 `img_decode_file` 报结果，不进页面），并补 help 行 + `#include "img_decode.h"`。

### 构建 + 烧录 + 验收（Release，0 错 0 警，Verified OK）
- 增量构建通过。FLASH 18.77% / RAM_D1 92.35%（链接期 RAM_D2 0.00%——池改运行时分配，去掉 8KB 静态）。
- OpenOCD 烧录 `build-release/nes_h743.elf` → **Verified OK**。
- 新增 `scripts/verify_img.py` 真机验收 **PASS**：
  - `cap` 生成 `1:/catch/12-17-14-114.jpg`（4:4:4, 21148B）。
  - `img decode 1:/catch/12-17-14-114.jpg` → `OK img decode JPEG 240x240 -> 240x240 21148 B`（此前同一文件必报「内存不足」）。**根因修复确证**。
  - 缺文件优雅拒绝 `ERR img decode failed: 文件打不开`，不崩。
  - 解码后 `status` 仍响应、`sram d2 294872/294912 (100%)` → 32KB 池**分配+释放无泄漏**。

### 结论
- 图片查看器「内存不足」系静态 8KB 工作区小于 TJpgDec(JD_FASTDECODE=2) 的 9644B 最坏需求；改用运行时从共享池取 32KB 后彻底解决。`img show`/`img decode` 共用同一 `img_decode_file`，故 UI 路径同样修复。

## 2026-08-14（再续9）— 图片查看器「涂抹」修复（JPEG RGB565 字节序）

### 需求（用户）
- 图片查看器显示文件**涂抹**（其它功能正常），修复后再做压力检测。

### 根因
- JPEG 走 TJpgDec（`third_party/tjpgd`），`tjpgdcnf.h` 设 `JD_FORMAT=1`（直接输出 RGB565）。`tjpgd.c` 的 `outfunc` 末尾有 `jd->swap` 分支：`swap=0` 输出标准 RGB565（R 在高字节）；`swap=1` 把每个像素高低字节交换 → ST7789（SPI6 16 位模式、MSB 先发）收到交换后的字节，R/B 通道错乱 = 视觉「涂抹」。
- **关键**：`jd_prepare()` 会 `tmp=jd->swap; memset(jd,0); jd->swap=tmp;` —— 即 `swap` 字段被**保存并恢复**，不被清零。而 `img_decode.c` 的 `decode_jpeg()` 里 `JDEC jd;` 是**未初始化栈变量**，`jd.swap` 保留栈垃圾。Release(-O2) 栈布局不同于 Debug(-Og)，若恰好非零即触发本 bug（与「某些构建/某些次才涂抹」现象吻合）。
- BMP 路径用 `rgb565()` 直出标准 RGB565、无 swap 字段 → 本就不受影响；NES 调色板亦为标准 RGB565 → 显示正常。这正印证「其它功能正常」。

### 改动
- `app/img_decode.c` `decode_jpeg()`：在 `jd_prepare()` 之前显式 `jd.swap = 0U;`（并加注释说明 `jd_prepare` 保存/恢复 swap 的陷阱与 ST7789 期望的标准非交换 RGB565）。一行修复。

### 验证
- **主机侧回归测试** `tests/test_jpg_rgb565.c`：逐字抽取 `tjpgd.c` 的 RGB565 转换代码，喂红/绿/蓝/白/黑/灰 RGB888：
  - `swap=0`（修复后）= 标准 RGB565，与 NES 调色板 / BMP `rgb565()` **逐位一致**（ref 0xF800/0x07E0/0x001F…）。
  - `swap=1`（未初始化 buggy）= 干净字节交换（红 0xF800→0x00F8 等），即「涂抹」症状。
  - `gcc -DJD_FORMAT=1` 实跑 → **ALL CHECKS PASSED**。
- **Release 构建**：`cmake -B build-release -DCMAKE_BUILD_TYPE=Release` → 0 错 0 警（FLASH 393704B / RAM_D1 484200B）。
- **真机烧录+压测（已执行，本机 ST-Link 接入）**：见下方「真机压测结果」。
  - 新增 `scripts/stress_img.py`：30 轮 `cap`→`img decode`(4:4:4 JPEG)→`img show`→`img close`，每轮断言控制台存活 + `sram d2` 完整回收（泄漏 ≤256B），最终 SRAM 基线校验。语法已校验。
  - 用户需在**已连接板**上：`openocd -f openocd.cfg -c "init" -c "program build-release/nes_h743.elf verify reset exit"` 烧录，再 `python3 scripts/stress_img.py [rounds] [comport]` 跑压测（建议先 `taskkill` 残留 openocd/gdb 以解 LIBUSB_ERROR_ACCESS）。

### 真机压测结果（ST-Link V2J38M27 接入，COM6/COM9 双串口在线）
- **烧录**：`openocd -f openocd.cfg -c "init" -c "program build-release/nes_h743.elf verify reset exit"` → **Verified OK**（STM32H74x 双 bank 2048K）；固件 `build Aug 14 2026 20:29:26`。

  - SRAM_D2 基线 **294872/294912** → 30 轮后仍为 **294872/294912**（delta=0，零泄漏）；`sram dtcm 131032/131072`。
