## NES 静态内存→动态内存池（为相机让出 DTCM/RAM_D2，重大）
- 需求（用户原话）：「nes区域直接定死被占用了，修改为动态内存管理，只是在打开nes模拟器时占用，其它时候可以被其它应用访问，这样可以后续实现相机应用提供足够内存。」
- 根因定位：`third_party/nes/nes_main.c` 中 `s_machine`(`.dtcm` ~82KB) 与 `s_rom`(`.ram_d2` ≤256KB) 作为**链接期静态变量**永久钉死两块 SRAM；就算 NES 没运行也一直占着。NES 核心本身是 `g_nes` 指针单体（各 TU `g_nes->` 访问），所以只需把两个静态缓冲改为运行时分配/释放即可。
- 方案（最小侵入，不碰 MPU、不碰 NES 运行/blit/帧循环逻辑）：
  - 新增 `bsp/sram_pool.h`/`bsp/sram_pool.c`：**边界标记（boundary-tag）空闲链表分配器**，两区 REGIONS[DTCM]={0x20000000,128K}、REGIONS[D2]={0x30000000,288K}。每块 8B 头(size|USED_BIT)+8B 尾(存 size|USED_BIT)，MIN_BLK=32B，payload 8 字节对齐；前导 prologue(used,锚定前端)+尾随 epilogue(used,size 0,终止扫描)；`sram_free` 与前后空闲块合并(coalescing)，避免开/关循环碎片。API：`sram_pool_init`(幂等)/`sram_alloc(region,size,align)`/`sram_free`/`sram_free_bytes`/`sram_total_bytes`。`align` 参数暂保留接口（NES 用 8/4 自然对齐，已 `(void)align` 防告警）。
  - `nes_internal.h`：`extern nes_t *const g_nes;` → `extern nes_t *g_nes;`（去 const 以便 `g_nes = s_machine` 赋值）。
  - `nes.h`：新增 `int nes_open(void);`/`void nes_close(void);`。
  - `nes_main.c`：`s_machine`/`s_rom` 改为 `NULL` 指针，`g_nes=NULL`；新增 `nes_open()`（`sram_alloc` DTCM 机器态 + D2 ROM 镜像，任一失败回滚释放并返回 -1）、`nes_close()`（释放两块、`g_nes=NULL`）。原 `nes_rom_arena()`/`nes_rom_arena_size()` 仍返回 `s_rom`/`NES_ROM_MAX`。
  - `page_nes.c`：`nes_enter()` 在 `find_roms()` 前 `nes_open()`（失败打印 `cannot allocate emulator memory`）；`nes_exit()` 末尾 `nes_close()`；`load_rom_named()` 加 `nes_rom_arena()==NULL` 守卫兜底（内存不足→`s_fail_reason="内存不足"`）。
  - `STM32H743ZITX_FLASH.ld`：删 `.dtcm (NOLOAD)` 与 `.ram_d2 (NOLOAD)` 两段（否则链接器仍预留空 NOLOAD 区），顶部「Memory notes」注释改写说明改由 `sram_pool` 运行时管理；MEMORY 区仍声明 DTCMRAM/RAM_D2（供池锚定基址，不放置 section）。
  - `CMakeLists.txt` PROJECT_SRCS 加 `bsp/sram_pool.c`；`app_main.c` `application_init()` 在 `bsp_console_init(); bsp_key_init();` 后调 `sram_pool_init();`；`app_cmd.c` `cmd_status()` 在 `cache` 行后加 `sram dtcm:`/`sram d2:` 空闲量上报。
- 构建验收：Release `ninja -C build-release` **0 错 0 警**；DTCMRAM=**0B**、RAM_D2=**0B**（原 62.82%/88.89% 已移除），RAM_D1 71.29%、FLASH 17.23%。Debug 同样 0 错 0 警、两区 0 占用。

## 魂斗罗打不开：内存重新划分（缺陷 #5）
- 用户报「魂斗罗显示内存过大，无法打开，重新划分内存布局允许执行」。
- 根因：`NES_ROM_MAX=256KiB` 钉死 ROM 缓冲；256KiB 级卡带 `.nes` 文件=256KiB+16B iNES 头=262160B > 256KiB → `nes_load()` `image_size>NES_ROM_MAX` 返 `NES_ERR_SIZE`(too large)；`page_nes.c` `load_rom_named()` 也因 `size>nes_rom_arena_size()` 报「文件过大」。
- 修复：`nes.h` `NES_ROM_MAX` 256*1024 → **286*1024**(292864B)，即 ROM 缓冲由「钉死 256KiB」改为「撑满整个 RAM_D2（288KiB 中可用约 286KiB）」，机器态仍留 DTCM；`nes_main.c` 顶部 Memory placement 注释同步改写。`nes_open()` 的 `sram_alloc(SRAM_REGION_D2, NES_ROM_MAX, 4U)` 自动受益。链接期 DTCM/RAM_D2 仍 0 占用。
- Release 0错0警、烧录 Verified OK（build 18:25）。
- **真机验证（COM6，`scripts/verify_contra.py`）**：`rom list` 见 `3 魂斗罗.NES`；`rom load 3` 后 **不再报 too large**，D2 成功分配 286KiB（空闲 ~294864→1992B）→ 内存过大已解决。

## 实现 mapper 23（VRC2/VRC4）— 魂斗罗终于可玩（缺陷 #6）
- 用户经 AskUserQuestion 选择「实现 mapper 23」。
- **关键判定**：调试 header `mapper=23 flags6=0x70 flags7=0x10 prg=8 chr=16` 与 NES 头库对照 → 该「魂斗罗.NES」即 **Contra (Japan) KON-RC826 / KONAMI-VRC-2 = VRC2b**（submapper 3），非 VRC4 专有。VRC2 是 VRC4 子集且共用 VRC4f 寻址，故按 **VRC4 仿真 mapper 23**，stride 默认 **1**（A0/A1 选低/高 4bit 半字节，覆盖 VRC2b/VRC4f）。iNES1.0 不记子变体，VRC4e(stride-4) 暂未覆盖（注：该卡带 $6000 1-bit latch 按 WRAM 兼容处理，与现有 $6000-$7FFF PRG-RAM 路径一致）。
- 改动：
