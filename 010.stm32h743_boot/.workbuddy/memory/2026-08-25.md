## verify.json 解析失败根因与修复（mini_json 只能取第一个 key）
- 现象：U 盘识别到 verify.json，但 `mjson_get_*` 返回非零 → 报 `verify.json fields missing/invalid`。
- 根因：`third_party/mini_json/mini_json.c` 的 `json_find_value()` 在"当前 key 不匹配"时只把 `i` 推进到 key 字符串结尾引号（`i=ke+1`，停在 `:` 上），未跳过整个 value；下一轮 `json_skip_ws` 对 `:` 无效 → `json[i]!='"' → return -1`。后果：该解析器只能正确提取文档**第一个 key**，其余 key 全失败。
- 修复：`json_find_value()` 非匹配分支改为 `i = json_skip_value(&json[i])`（跳过整个 value：字符串/数字/true|false|null/嵌套 {}[]/裸 token），再继续找下一个 key。
- 验证：host 单元测试（`test_mini_json.exe`，gcc 编译 fixed mini_json.c）对真实格式、乱序、紧凑单行三种 JSON 均 PASS（已清理测试产物）。
- 含修复的 bootloader 已重编（13:28, 110740B, `json_find_value` 入 elf, 零警告）。注意：该修复在 **bootloader 侧**，用户必须把新 `stm32h7_boot.bin` 烧进内部 Flash 才能生效，仅换 U 盘里的 app 包无效。

## BFLASH_ProgramBlock 卡死根因与修复（Cortex-M7 DTCM 不可执行）
- 现象：升级流程进入 `BFLASH_ProgramBlock` 后死机于 startup 的 `Infinite_Loop`（`Default_Handler`）→ HardFault/BusFault。
- 根因（map 铁证）：擦写引擎（`.upgrade_ram`：BFLASH_EraseApp/EraseAppLastSector/ProgramBlock/VerifyBlock + flash_* 辅助）全部链接在 **DTCM 0x20000000**；而 **Cortex-M7 的 I-Code 总线无法从 DTCM 取指**（DTCM 仅供数据，TCM 硬件约束，MPU 的 XN=0 也管不到）。跳进 DTCM 函数第一条指令即 BusFault。原 MPU 注释误称"DTCM 放 upgrade engine"，是错误认知。
- 修复：链接脚本 `stm32h743xix_flash.ld` 把 `.upgrade_ram` 从 `>DTCM` 改到 `>SRAM1`（0x24000000 AXI SRAM，可执行、且独立于两个 Flash bank）；MPU region2 已将其标 XN=0 可执行；`.data` 紧随其后（0x240004e8），无重叠。同时给 `addr_to_bank_sector` 补 `UPGRADE_RAM`（原在 `.text`/bank1 Flash，调用链残留 Flash 调用，已内联进 RAM 函数）。
- 验证：重编 bootloader 零警告（111124B，13:51）；map 确认引擎全在 0x24000000、DTCM 无引擎函数；`_eupgrade_ram=0x240004e8`，`.data` 起始 0x240004e8 无重叠。已烧录内部 Flash（仅擦 sector0，app/config 保留）并 Verify OK。
- 结论：H7 上从 RAM 跑 flash 擦写引擎，**绝不可用 DTCM**，必须放 AXI SRAM/SRAM1-4（可执行且非 bank1）。这是通用坑，后续 H7 bootloader/flash 工程都适用。

## BFLASH_ProgramBlock 仍卡死 → 改用验证过的 HAL 写入路径（参考 7.stm32h7_iap）
- 现象：引擎已移到 AXI SRAM（DTCM 问题修掉后），擦除（BFLASH_EraseAppLastSector 同在 RAM）正常，但 `BFLASH_ProgramBlock` 仍死 `Infinite_Loop`。用户排除 ICache/数据越界两类假设。
- 排查结论：① ICache 在本 bootloader 全程禁用，MPU region0/2 均 Normal Non-Cacheable(C=0)，ICache 不可能缓存 0x24000000；② `g_io_buf`(0x24002420, 4096B align32) 与引擎(0x24000000~0x240004e8) 不重叠、chunk≤4096 不越界。③ H7 的 RWW 只 **stall 不 fault**，从 bank1 取指编程 bank1 不会 HardFault。故两类假设均不成立。
- 根因定位方向：手搓寄存器版 `flash_program_word` 与 HAL `HAL_FLASH_Program(FLASH_TYPEPROGRAM_FLASHWORD,...)` 序列本质一致，但既有工程已有一份**经过真机验证**的升级代码（`coding_git/embeds/stm32h7_project/7.stm32h7_iap` 的 drv_flash.c / upload_frame.c），直接采用其通路最稳。
- 修复：`bsp/flash_upgrade.c` 的低层引擎改为走 HAL：擦除用 `HAL_FLASHEx_Erase()`（VoltageRange=FLASH_VOLTAGE_RANGE_3）；编程用 `HAL_FLASH_Program(FLASH_TYPEPROGRAM_FLASHWORD, addr, (uint32_t)src)`；每次操作前 `__HAL_FLASH_CLEAR_FLAG(FLASH_FLAG_ALL_ERRORS_BANK1/2)` 清双 bank 错误标志，`__disable_irq()`+`HAL_FLASH_Unlock()` 包住、`HAL_FLASH_Lock()`+`__enable_irq()` 收尾（与参考 drv_flash.c 的 `flash_update_write_device` 一致）。保留 `.upgrade_ram` 放 AXI SRAM + `BFLASH_Relocate()`（避免 RWW stall），公共 API 与 config/version 辅助函数不变。
- 验证：Debug 零警告重编（text 109808B / data 2268B / bss 38824B）；map 确认 `BFLASH_ProgramBlock`/`flash_erase_sector`/`flash_program_word` 全在 0x24000000（`_eupgrade_ram=0x240002c8`），HAL 函数仍在 bank1 Flash；新 `stm32h7_boot.bin`(112116B) 已拷 `test_app/dist/`。真机编程需用户在 U 盘放入包并接 U 盘复位触发。
- 经验：H7 内部 Flash 升级，**直接用 HAL 的 FLASHWORD 编程 + 操作前清双 bank 错误标志** 是最稳路径；手搓寄存器极易踩 PSIZE/序列细节。参考 `7.stm32h7_iap` 是黄金样本。
