### 关键坑（Git Bash + Windows 环境构建 Zephyr）
1. **不要 export POSIX 格式的 ZEPHYR_BASE**（`/d/data/...`）——west build 会读它并传给原生 Windows cmake，导致 `pristine.cmake` / 路径解析失败。正确做法：不 export（让 west 从 west.yml 解析 Windows 路径），或 export Windows 路径 `D:/...`。
2. **GNUARMEMB_TOOLCHAIN_PATH 必须用 Windows 路径**（`D:/Software/tools/arm-none-eabi`），不是 `/d/...`。
3. 残留的 `build/CMakeCache.txt` 里若缓存了坏 ZEPHYR_BASE，`-p always` 的 pristine 会复用坏值；直接删 build 目录（python shutil，绕开沙箱 rm 包装）再重构建。
4. west.yml 每个 project 必须有 `remote`（remotes + defaults），否则 `west build` 命令无法加载。

### Zephyr 3.7.0 LVGL 模块差异（相对旧版 glue）
- **无 `LV_Z_DISPLAY_DEV_NAME`**：显示通过 chosen `zephyr,display = &DISPLAY` 自动绑定。
- **tick 由 `LV_TICK_CUSTOM=1` + `k_uptime_get_32()` 提供**（`zephyr/modules/lvgl/include/lv_conf.h`），因此 `lv_tick_inc()` 不存在（`lv_hal_tick.h` 里 `#if !LV_TICK_CUSTOM` 才声明）；应用循环只需 `lv_timer_handler()`。
- 无 `LV_USE_OBJ` 开关（obj 是 LVGL 核心对象）；FatFs 卷数符号不是 `FS_FATFS_MAX_VOLUMES`（默认 2 由 disk 驱动注册决定）。
- `CONFIG_LV_COLOR_DEPTH=16` 不能直接赋值（无 prompt 的 int，由 `LV_COLOR_DEPTH_16` choice 推导）；`CONFIG_BOARD`/`CONFIG_BOARD_QUALIFIERS` 同理不能进 prj.conf（由 `-b` 传参）。

## SD 卡挂载失败排查（真机，SD 卡本身正常）

串口报 `FONT: f_mount failed FRESULT=3 (FR_NOT_READY)`。逐层定位出两个根因：

1. **SDMMC 时钟 ≠ 48MHz**：STM32H743 SDMMC 时钟源是 PLL1Q（`STM32_SRC_PLL1_Q SDMMC_SEL(0)`），
   而 `sdmmc_stm32.c` 在 `CONFIG_SDMMC_STM32_CLOCK_CHECK=y` 下强制要求 `sdmmc_clock_rate == MHZ(48)`，
   否则 `return -ENOTSUP`。原 PLL1Q=480MHz（div-q=2）。
   修复：`&pll { div-q = <20> }` → PLL1Q=960/20=48MHz。同时 `&sdmmc1` 加 `bus-width=<4>` + `idma`。
2. **FatFs 卷名错误**：Zephyr 设 `FF_STR_VOLUME_ID=1`（字符串卷名），
   `FF_VOLUME_STRS="RAM","NAND","CF","SD","SD2",...`，逻辑盘符必须用 `SD:`（配合
   `CONFIG_SDMMC_VOLUME_NAME="SD"`），不能用数字 `1:`。之前误设 `"1"`/`"1:"` 导致挂载失败。

修复后真机串口：`FONT: UNIGBK=1 GBK12=1 GBK16=1 GBK24=1 GBK32=1`（字库全部加载），
halt PC 落在 `mipi_dbi_spi_write_helper`（OLED 刷新），中文渲染链路全通。

### 关键结论（Zephyr STM32H7 SDMMC + FatFs）
- SDMMC 时钟源只有 PLL1Q/PLL2R 两选（1 位 SDMMC_SEL），驱动要求 48MHz。
- FatFs 逻辑盘符是**字符串**（`SD:`），不是裸机时代的数字 `1:`。
- 最终资源：FLASH 249620B/2MB=11.90%，RAM 164368B/512KB=31.35%，零警告。

## 屏幕黑屏 + LED 不闪排查（真机）

用户反馈屏幕无显示、LED 不闪。逐层定位出三个问题：

1. **LED 引脚错误**：原用 nucleo 的 `leds/green_led`（PB0），用户板 LED 实为 **PG7**
   （裸机 `main.h`：`LED_Pin=GPIO_PIN_7`）。overlay 用 `&leds { green_led{...} }` 覆盖
   是**新增子节点**（导致两个 LED 节点、index 0 仍是 PB0），必须用**节点名 `led_0`**
   覆盖（unit name），标签可保留。修复后 zephyr.dts `led_0: gpios=<&gpiog 0x7 0x0>`。
   真机验证：GPIOG ODR bit7 以 500ms 周期翻转 ✓。
2. **ST7789 显示开启（DISPON）缺失**：Zephyr st7789v 驱动 init **不发 DISPON(0x29)**，
   LVGL glue（lvgl_display.c）也不调 `display_blanking_off`（仅 EPD 路径调）→ 屏
   保持 sleep-in 全黑。裸机 init 末尾有 0x29。修复：main.c 步骤 1b 调
   `display_blanking_off(DEVICE_DT_GET(DT_CHOSEN(zephyr_display)))`。
3. **ST7789 软件复位延时不足**：无 RST 引脚时 `mipi_dbi_spi_reset` 返回 -ENOTSUP，
   st7789v 走 SWRESET(0x01)+5ms 分支；ST7789 tRES≈120ms，复位未完成时后续命令
   （含 SLPOUT）全被忽略 → 永远 sleep-in。patch `display_st7789v.c`：
   `k_sleep(K_MSEC(5))` → `k_sleep(K_MSEC(120))`（对齐裸机上电 10ms 后直接配置）。
   注意：patch 会被 `west update` 覆盖，需记录重新应用。

### 裸机 vs Zephyr 同步分析结论（SPI6/ST7789）
- SPI6 时钟：裸机 `RCC_SPI6CLKSOURCE_D3PCLK1`（APB4=120MHz/2=60MHz）；
  Zephyr `clocks=<&rcc 0xf4 0x20>` 即 APB4ENR.SPI6EN，内核时钟同为 APB4（D3PCLK1），
  自动分频到 mipi-max-frequency=20MHz —— 一致，非问题。
- SPI 模式：裸机 CPOL=0/CPHA=0（Mode 0）；Zephyr st7789v 的 dbi_config operation
  无 CPOL/CPHA 位 = Mode 0 —— 一致。
- DC=PG15（dc-gpios <&gpiog 0xf 0x0> 高=数据）、CS=PG8（低有效）、BL=PG12 均正确。
- 寄存器参数（vcom/gctrl/vrhs/vdvs/mdac/colmod/lcm/porch/pwctrl1/pvgam/nvgam）与
  裸机逐条一致；Zephyr 额外发 0xDF CMD2EN（裸机无，无害）。
- 真机最终验证：SPI6 SR=0x1002（TXP+TXC，无 OVR/UDR/MODF），PC 在内核调度路径，
  渲染活跃，DISPON 已发（display ready + blanking_off 执行）。

## 字体问题修复（中文不显示 + ASCII 虚化，真机）

屏幕显示正常后，用户反馈：1) 字体非 SD 的 GBK、虚化严重；2) 中文无法显示。

### 根因 1：UNIGBK.BIN 是"双段表"，整表二分必失败
真机 dump（串口 + 线性扫描）确认 UNIGBK.BIN（174344B = 43586 条记录）结构：
- **段 1**（idx 0-21791，21792 条）：`[uni_lo,uni_hi,gbk_lo,gbk_hi]` 按 **Unicode 升序**
  （符号 + 全部汉字，`中 U+4E2D → GBK D0D6` 在 idx=762）；
- 1 条全 0 填充（idx=21792）；
- **段 2**（idx 21793-43584）：`[gbk_lo,gbk_hi,uni_lo,uni_hi]` 按 **GBK 升序**
  （`gbk 0xFE4D→uni 0xFA27` 等）。
两段排序键不同 → 对全表按 uni 二分，首跳 mid=21793 就落进段 2/GBK 区，永远找不到。
修复：`unigbk_find_seg1()` 初始化时找第一条全 0 记录定位段 1 边界（缓存），
`lcd_driver_unigbk_lookup()` 仅在段 1 内二分。自检：`lookup 0x4E2D -> OK (gbk D0D6)`。
裸机项目根本不用 UNIGBK（源码直接 GBK 编码），所以此问题只在 Zephyr(UTF-8) 侧暴露。

### 根因 2：ASCII 用 Montserrat_14 抗锯齿字体 → 虚化
gbk 字体桥对 <0x80 返回 false → 回退 Montserrat（14px 抗锯齿），与 16px 点阵中文
混排被放大渲染，明显发虚。
修复：从裸机 `ASCII_1608_Table`（95 字符 0x20-0x7E，8×16，LSB 行扫描）移植，
Python 脚本逐字节位反转为 **MSB-first**（LVGL 1bpp 约定，`lv_img_buf.c` 用
`1 << (7-bit)`），生成 `bsp/ascii_1608_table.c/.h`；新增 `gbk_ascii_font_16`
点阵字体作为所有 gbk_font 的 fallback。

### 验证
- 编译零警告，FLASH 12.00%（ASCII 表 +1520B）、RAM 31.35%。
- 串口：`lookup 0x4E2D -> OK (gbk D0D6)`，字库 5 文件全加载。
- halt PC 在 `z_impl_gpio_port_set_bits_raw`（mipi_dbi 切换 DC/CS 渲染像素）。
- 中文=SD GBK 16×16 点阵，ASCII=8×16 点阵，均清晰。

## 中文映射错字修复（"时钟"→"笔又"类，真机）+ UI 美化

### 根因：UNIGBK gbk 字段字节序（小端）
多字自检对照标准 GBK 发现：`lookup` 返回的所有 GBK 码高低字节颠倒
（时=B1CA 应 CAB1、钟=D3D6 应 D6D3、文=C4CE 应 CEC4、主=F7D6 应 D6F7…），
只有对称字（中 D6D0→D0D6 读反、行 D0D0）碰巧对。
UNIGBK 记录的 **gbk 字段也是 little-endian（[lo,hi]）**，代码却按
`gbk_out[0]=rec[2]; gbk_out[1]=rec[3]` 直接返回 → 全反 → .FON 索引错位。
修复：`gbk_out[0]=rec[3]; gbk_out[1]=rec[2]`（返回常规 hi,lo 顺序）。
修复后全部标准：中 D6D0 文 CEC4 时 CAB1 钟 D6D3 主 D6F7 字 D7D6 频 C6B5
又 D3D6 笔 B1CA 运 D4CB 行 D0D0 ✓。
