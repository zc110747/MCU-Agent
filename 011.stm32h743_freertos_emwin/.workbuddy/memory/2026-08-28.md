# 2026-08-28  emWin 工程构建修复

## 关键修复（STM32H743 + STemWin CMake 工程）
1. **STemWin 与 binutils 2.44 不兼容**：arm-none-eabi-gcc 15.3.1 (ld 2.45.1)
   链接 STemWin_CM7_wc16.a 报 `Unknown destination type (ARM/Thumb)`。
   必须用 binutils <2.44 工具链（已装 GNU Arm Embedded 14.2.rel1，ld 2.43.1，
   路径 D:/Software/arm-gnu-toolchain-14.2.rel1）。

2. **工具链必须绝对路径锁定**：仅把 14.2.rel1 的 bin 加到 PATH 仍会回退到 PATH
   上靠前的 15.3.1（tools/arm-none-eabi）。修复：cmake/gcc-arm-none-eabi.cmake
   将编译器/链接器/ar 等绝对路径 `FORCE` 写缓存，并加 `-B<tc_bin>` 让 gcc 驱动
   优先在 14.2.rel1/bin 找 ld/as。Windows 上绝对路径需带 .exe 后缀（CMake 严格
   存在性检查不做 PATHEXT 补全，否则报 "not a full path to an existing compiler"）。

3. **STemWin .a 链接方式**：不能把 .a 直接塞进 add_executable 源列表（CMake 静默
   丢弃），改用 `add_library(stemwin STATIC IMPORTED)` + target_link_libraries
   包裹 --start-group/--end-group。

4. **LCD_* 符号多重定义**：drv_spi_oled.c 从 003 LVGL 工程带入的 LCD_SetColor 等
   高层 API 与 emWin 库内部 LCD_SetColor 撞名。已统一重命名为 OLED_*（保留 emWin
   的 LCD_X_* 回调与 static LCD_SPI_*）。

5. **wchar_t 链接告警**：STemWin 用 2 字节 wchar_t、newlib 用 4 字节，加
   `-Wl,--no-wchar-size-warning` 抑制。

## 补充修复（build_oneclick.bat 解析错误 "此时不应有 into。"）
1. **父块内展开含 `)` 的变量**：原脚本在 `if defined TC_BIN ( ... ) else ( ... )` 块内执行
   `set "PATH=%TC_BIN%;%PATH%"`。cmd 的块解析器在变量展开【之前】就扫描 `)`，而用户 PATH
   含 `Program Files (x86)` 的 `)`，会提前闭合 `if` 块，使后续 token 被重新解析并报
   `此时不应有 into。`（PowerShell 下 `.\build_oneclick.bat` 暴露）。
   - 修复：把 `set "PATH=..."` 移出 `()` 块（改为独立语句 `if defined TC_BIN set "PATH=..."`），
     echo 保留在块内、warn 改为独立 `if not defined TC_BIN (...)`。引号 RHS 使 `)` 被当作字面量，
     不再提前闭合块。已在 .bat 内加 REM 说明该坑。
   - 经验：Windows .bat 父块内不要展开可能含 `( ) & |` 的环境变量（尤其 PATH）；要么移到块外，
     要么用延迟扩展（`setlocal EnableDelayedExpansion` + `!VAR!`）。

2. **端到端验证**（clean 双构 + 烧录）：
   - Debug:   FLASH 133532 B / 2MB (6.37%), RAM 271808 B / 512KB (51.84%), 0 警告
   - Release: FLASH 132860 B / 2MB (6.34%), RAM 271808 B / 512KB (51.84%), 0 警告
   - openocd -f openocd.cfg -c "program build/emwin_oled.elf verify reset exit" → Verified OK

## 补充修复 2（build_oneclick.bat 二次崩溃："'-click' 不是内部或外部命令" 等 token 碎片）
1. **根因：LINE ENDING 被破坏（LF 而非 CRLF）**。上一次 Edit 把 .bat 重写成纯 LF（Unix）行尾，
   而 Windows `cmd.exe` 解析 .bat **必须 CRLF**。纯 LF 时 cmd 无法正确断行，把整文件按空格/换行
   当成一串命令逐 token 执行，于是出现 `-click`/`ject`/`rrorlevel`/`%T`(%%T 未展开) 等碎片报错，
   末尾 `此时不应有 .。` 是 cmd 在 `cmake -S . -B build` 的 `.` 处崩。
   - 验证：`od` 显示首行 `40 65 63 68 6f 20 6f 66 66 0a`（0a=LF，无 0d）；`tr -cd '\r'` 计数=0、LF=151。
   - 修复：`tr -d '\r' | awk '{ printf "%s\r\n", $0 }'` 转回 CRLF（CR=151/LF=151，首字节变 `...0d 0a`）。
2. **次生坑：.bat 内混入了中文（UTF-8）**。我加的 REM 注释含 `"此时不应有"`，在中文 Windows GBK
   控制台下 UTF-8 中文字节可能干扰解析（本项目 .bat 早前已"去中文"）。已改为纯 ASCII：`(parse error)`。
   - 教训：**编辑 Windows .bat 后必须 (a) 确认仍是 CRLF，(b) 确认无中文/非 ASCII**。Edit 工具可能在某些
     写入路径产出 LF 或保留非 ASCII；改完用 `od`/`grep -P '[^\x00-\x7F]'` 复查。
3. 本环境 Bash/PowerShell 均禁止调用 cmd.exe，无法在此直接跑 .bat；只能改完用 `od`+`grep` 复查，
   并以等效 cmake/ninja 命令独立验证构建链路（已确认 Debug/Release 双构 0 警告）。

## ⚠️ 最终根因修正（2026-08-28 傍晚，实证推翻早先两条理论）
上文「补充修复」「补充修复 2」把 `此时不应有 into。` 归因于 PATH 父块/行尾，**均非最终根因**。
用最小 bat 二分复现（test_bat1~4，PowerShell `&` 跑 + 日志落盘）后锁定：
1. **真正根因（一直存在）**：`build_oneclick.bat` 第 87 行 echo 文本 `Copy third_party (FatFs and
   STemWin) into this folder` 里的 **`(FatFs and STemWin)` 括号**——它位于 `if not exist ... ( ... )`
   块内，cmd 解析块时 `)` 提前闭合块，残留 `into ...` 成非法 token → `此时不应有 into。`；条件为假
   也照样先解析报错。同理 Step 3 的 `echo [ERROR] Configure (Debug) failed.` 等 6 处 `(Debug)`/
   `(Release)`。用户本地已按 stm32-project-scaffold 技能「致命坑 3」清掉全部块内 echo 括号
   （`Debug` 取代 `(Debug)`），并补「致命坑 4」修复（`%~dp0` 尾斜杠剥离 + for 块内 `2>nul`）。
2. **PATH 父块/行尾结论修正**：`set "PATH=%TC_BIN%;%PATH%"` 移出父块属于无害改进，但并非本错误根因
   （test_bat1 证明该行在隔离环境完全正常）；LF 行尾是 Agent 编辑引入的二次问题（已修复，4.8）。
3. **沙箱 ACL 坑**：Agent 沙箱/提权建的 build/、build-rel/ 文件 ACL 异常，用户侧 cmake 生成阶段报
   `ninja: error: failed recompaction: Permission denied` → 删除 build build-rel 由脚本重建即解决（4.9）。
4. **最终验证**（PowerShell `& .\build_oneclick.bat` 全流程）：[STEP] Configure/Clean/Build Debug +
   Release 全部 145/146 通过，`[DONE] Build succeeded.`，BAT-EXIT=0，**零警告**；
   Debug FLASH 133532B(6.37%) / Release 132860B(6.34%)，RAM 271808B(51.84%)。
   已把「4.8 LF+中文破坏 .bat」「4.9 沙箱 build 目录 ACL」补进 stm32-ai-dev-environment 技能。

## 用户二次反馈修复（同一天，仅 Debug 构建）
用户实际跑起来后报两个现象：① 无串口打印；② emWin 字体不正确、也无正确图标。
1. **问题①根因**：UART1(PA9/PA10) 初始化 + syscalls.c `_write`→`huart1` 重定向本就正确，
   但应用层从不调用 `printf` → 静默无输出。修复：Application/app_main.c
   application_init() 各启动阶段加 `[boot]` 日志、application_run() 1Hz 心跳加 `[tick]` 日志
   （含 uptime / font_mask / 字库缓存 hit/rd）。MX_USART1_UART_Init() 在 application_init 之前调用，
   开机日志时 huart1 已就绪。printf 走 newlib-nano 整数格式化（无 float），零警告。
2. **问题②根因**：emWin 自定义字体 emwin_font_gbk.c 的 draw 例程旧版按 **LSB 行扫描** 取位，但
   编译进固件的 ASCII 字模(ASCII_Fontxx)是 **MSB 行扫描**，导致所有数字/英文/标签水平镜像
   （中文经 lcd_driver_get_hzmat 的 Convert_Font_MSB_Column_to_LSB_Row 已转 LSB 行扫描故原本正常）。
   修复：draw_lsb_rows 增 `msb_first` 参数 —— ASCII 传 1(MSB 行扫描)、中文传 0(LSB 行扫描)。
   用 Python 脚本抽取 ASCII_1608_Table 渲染 '7'/'K'/'R'/'3'/'2' 验证：msb_first=1 字形正确、
   msb_first=0 镜像；'0' 因水平对称两者相同（已注明非判据）。
3. **关于"图标"**：本工程 app_ui.c 是 003 LVGL 面板的纯文本移植，无 bitmap 图标子系统；
   "图标不显示"与"字体不正确"同源（旧 ASCII 镜像），非独立缺陷。如需图形图标属新增 feature。
4. **构建结果（仅 Debug）**：0 error / 0 warning，FLASH 137128B/2MB(6.54%)、RAM_D1 271848B/512KB(51.85%)；
   产物 build/emwin_oled.{bin,elf,hex,map}。用户要求只出 Debug，不再出 Release。
