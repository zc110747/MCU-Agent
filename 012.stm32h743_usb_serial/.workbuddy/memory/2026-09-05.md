### 修复的三个真实固件缺陷
1. **环形缓冲满/空二义性**：`rb_free()` 用 `cap-used` 使"满"被判为"空"，生产者覆盖未消费数据
   （首轮 lost=3.6e10）。改为可用容量 `cap-1`（保留 1 字节）。
2. **7 数据位 + 校验时校验位污染数据**：STM32 字长含校验位，7E1/7O1 是 8 位字长，
   校验位落在 RDR bit7 被字节 DMA 读出。加 `s_rx_data_mask = (1<<data_bits)-1`，排空时就地掩蔽。
3. **RTS 配成 AF 模式导致实际悬空**（最隐蔽）：`HwFlowCtl=NONE` 时 USART 不驱动 RTS，
   而 `HAL_GPIO_WritePin` 对复用引脚无效 → PB14 高阻，短接的 PB0 被上拉读作"未就绪"，
   四种流控模式全 `CTS=0`。改为 `GPIO_MODE_OUTPUT_PP` 软件驱动，CTS 改 `GPIO_MODE_INPUT`+上拉。

### 固件侧新增的可观测量（都是排查关键）
- `rx_max`：接收环占用高水位（`rb_max_used`）——避免"查询时已排空"的测量竞态。
- `rts_off`：RTS 被去断言的累计次数，同样是粘性计数。
- `RTSO=`：本地 RTS 输出状态（区别于主机侧 `RTS=`）。

### 设计结论
- 带内命令通道（`+++` + AT）与 bulk 数据通路共口，流控把 TX ring 灌满后设备 NAK，
  逃逸序列也发不进去 → 必须保留 EP0 vendor 控制请求作为永不被背压阻塞的管理通道。
  压测脚本查询前需先 `drain_quiet()`。
- 经验已同步到 `stm32-peripheral-drivers` skill 新增「十二、UART DMA 桥 + RTS/CTS 流控」，
  用户级与工程级两份副本已一致。

## 追加：定长/定间隔/定量发送（`paced`）+ 延迟测量假象

用户请求三档测试（均未开启流控，`AT+FLOW?` 确认 `+FLOW: 0`）：

| 用例 | 帧数 tx/rx | 线路字节 | 延迟 min/avg/max | 错误 |
|---|---|---|---|---|
| 1 B × 100 帧 @10 ms | 100/100 | 1300 | 1.348 / 1.438 / 1.755 ms | 全 0 |
| 10 B × 100 帧 @20 ms | 100/100 | 2200 | 2.156 / 2.221 / 2.449 ms | 全 0 |
| 500 B × 20 帧 @500 ms | 20/20 | 10240 | 44.690 / 44.771 / 44.888 ms | 全 0 |

三档 `byte-exact yes`，复跑两次结果一致（±0.02 ms）。

**延迟模型**：`latency ≈ 0.31 ms + (12+N) × 10/115200`，三档残差均 < 15 μs。
`12` = 同步字 2 + 长度 2 + 序号 4 + CRC 4。残差近零 → 延迟完全由波特率决定，
固件/USB 无与长度相关的额外排队。

### ⚠️ 延迟测量假象（PC 侧，非固件缺陷，最有价值的一条）
首轮 1 B 小包测出 34 ms，用 `tools/latency_probe.py` 对照发现：
软件回环 `AT+LOOP=1`（完全绕过 UART/DMA）也是 31.91 ms → 锁定 PC 侧。
根因 `ser.read(ser.in_waiting or 4096)`：无数据时请求 4096 字节，
Windows 会**凑满才返回**，空等一整个读超时。改为 `ser.read(n if n else 1)`
→ 34.24 ms 降到 **1.43 ms**（软件回环 31.91 → 0.22 ms）。
**只在轻负载/空载时暴露**，灌满缓冲时 `in_waiting` 恒非零，症状消失。

固件固有延迟基线（可跨项目参考）：**软件回环 0.22~0.24 ms**，
UART4 @115200 每字节再加 86.8 μs。

## 追加：透明桥重设计（推翻 AT/vendor 双通道，改标准 CDC + 硬件流控自管理）

> 前序日志记录的 "AT/vendor 双配置通道 + EP0 vendor 管理通道" 设计已被**推翻**。
> 透明转发器不能在 bulk 数据里解析 `+++`/AT，配置只能走标准 CDC 控制传输。

### 设计决策（用户拍板）
- **去掉 in-band AT 命令机制**：透明转发，`+++`/`AT+*` 一律当数据；配置仅走
  `SET_LINE_CODING` / `SET_CONTROL_LINE_STATE`（标准 CDC 控制传输）。
- **不用独立控制通道**：WinUSB 第二接口 / EP0 vendor 请求都不允许。
- **改用 UART4 硬件流控**：`HwFlowCtl = UART_HWCONTROL_CTS`（CTSE 常开），USART 硬件采样 CTS(PB0)。
- **Windows usbser 决定性限制**：端口 open 后 RTS 状态变化**不转发**给设备（仅 DTR 触发
  `tud_cdc_line_state_cb`）；UART4 无 DTR 引脚 → "主机 RTS/DTR 配置流控"在 Windows 不可行
  → **流控必须固件自管理**（CTSE 常开 + RTS(PB14) 软件 GPIO 按 16KB 接收环余量驱动）。

### 关键引脚配置修正（已落地并双构验证）
- CTS PB0：`GPIO_MODE_AF_PP` + `GPIO_PULLDOWN`。浮空读成"就绪"，对端不驱动 CTS 时 TX 永不被
  门控（透明行为关键）。旧设计 `GPIO_MODE_INPUT`+PULLUP 错（CTS 读成高 → 门控不通）。
- RTS PB14：`GPIO_MODE_OUTPUT_PP` + `Alternate=0`。因 HwFlowCtl=CTS 而非 RTS_CTS，USART 不驱动
  RTS，`HAL_GPIO_WritePin` 对 AF 引脚无效 → 改软件 GPIO 驱动。
- DTR：无物理引脚，仅"观测"（`uart_bridge_dtr_asserted`），绝不门控数据通路。

### 验收（工具侧，回环可验部分）
- `transparency_probe.py`：DTR 开/关均 74/74 原样回显；`+++AT+FLOW=1` 作数据不被吞 → ALL PASS。
- `stress_test.py` 整文件重写（去 AT）：transparency + formats + paced 仍可用；`all` 透明验收全 PASS。
- paced 三档（**未开流控**，全 0 错误）：1B/10ms/100B avg 1.437ms、10B/20ms/1000B avg 2.232ms、
  500B/500ms/10000B avg 44.768ms。
- 固件内部计数器：无 in-band 统计通道，SWD 直读 `g_uart_stats`。

## 追加：用户质疑 "CTSE 为什么默认一直开"

用户原话："UART_HWCONTROL_CTS 为什么默认一直开，我没有提出此需求"。澄清与结论：

- **硬件 CTS 流控机制本身**是用户提的（透明桥重设计那轮："使用 UART4 的硬件流控不行吗"）。
- **"常开、不可由主机关闭"这个策略**是我的决定，非用户单独指定。三层约束迫使如此：
  ① 已去掉 in-band AT/vendor 配置通道（用户拍板）；② 标准 CDC 无流控开关字段
  （SET_LINE_CODING 仅波特率/格式，SET_CONTROL_LINE_STATE 仅 DTR/RTS）；
  ③ Windows `usbser.sys` 端口打开后不转发 RTS（仅 DTR）。
  → 主机无任何通道可发"开/关流控"，要兑现硬件流控只能固件常开。
- **常开对普通 peer 零副作用**：CTS(PB0) AF+PULLDOWN 且低有效，对端不驱动 CTS 时读 LOW=允许发送，
  TX 永不被门控，行为等同"流控关"；仅对真玩流控、拉高 CTS 的 peer 才门控。
- **代码脆弱点已修**：`uart_hw_apply()` 里 `huart4.Init.HwFlowCtl = UART_HWCONTROL_CTS;` 原先被注释掉，
  仅靠 `uart_bridge_init()` 先设、apply 继承；已改为 apply 内显式赋值（行为不变，双构零警告）。
- 待用户定策略：A 保持常开（推荐）/ B 改 `UART_HWCONTROL_NONE`（流控能力消失）。
