## DCMI 像素恒定值问题 — 已解决

### 根因
ST BSP 的 `OV5640_R320x240` 初始化表将 `0x3814`（水平采样增量）设为 `0x31`（2× 抽样），但**未使能** `0x3821 bit0`（水平 binning）。这是 OV5640 的非法组合——列地址生成器不推进，导致 DVP 在整行内反复输出同一个像素值。

症状：DCMI 时序完全正确（帧/行/字数精确），PCLK/HREF/VSYNC 正常，但数据总线在单行内恒定（DCMI_DR = 0x37373737 或类似常量）。异步 GPIO 采样证明传感器确实输出变化数据（HSYNC 高窗口 101 个不同值、低窗口 162 个不同值），排除了传感器故障。

### 解决方案
移植用户提供的已验证参考驱动（同款 STM32H743 + OV5640 硬件）的完整初始化表到 `Core/Src/ov5640_ref.c`，仅修改两项用于 UVC：
- `0x4300`: 0x6F → 0x30（RGB565 → YUV422/YUYV）
- `0x501F`: 0x01 → 0x00（ISP RGB → YUV422）

同时修正 DCMI 极性配置：
- PCKPolarity: FALLING → **RISING**（匹配 0x4740=0x21）
- VSPolarity: HIGH → **LOW**

### 验证结果
- `ov5640_ref_fail_index = -1`：200+ 寄存器全部写后读回校验通过
- `cam_words_per_frame = 0x7080 = 28800`：精确匹配 240×240×2/4
- `DCMI_DR` 从常量变为真实 YUYV 数据（如 `7e057f06`）
- 横向梯度 |dY/dx|: **0 → 1.01**
- 每行不同值: **1 → 31**
- 图像可见真实场景内容（斜边+纹理）

### 修改文件

## UVC 剧烈变化画面拼接(撕裂)问题 — 已修复并 A/B 验证

### 根因
原 uvc_app 在 USB 帧间隔到达时直接 `memcpy` DMA 缓冲(s_fb_base)。DMA 以 CIRCULAR 模式持续覆写 fb[0]，CPU 拷贝速度(~21× 快于 DMA)在任意相位拷贝会中途越过 DMA 写指针：前半部分为新帧、后半部分为旧帧，产生拼接缝(tearing)。静止场景因新旧帧相同而不可见，运动/剧烈变化场景暴露。旧代码在随机相位 memcpy 约 80% 概率撕裂(量化见下)。

### 解决方案：消隐期相位锁存 + 三缓冲
- `bsp_camera_snapshot(dst)`：门控在垂直消隐期(NDTR>=FRAME_SIZE/4，即满值 0x7080，约 16ms 窗口)才拷贝；拷贝后检查 NDTR 若已落后超过 1 行余量则判为撕裂并丢弃该帧(frame_done=false，下次重试)。
- 三缓冲：fb[0]=DMA 目标(fb_base)，fb[1]/fb[2]=发送侧交替缓冲(s_ready_idx 持有就绪帧，s_tx_idx 持有在线传输帧)。快照可在 USB 传输进行中与传输并行，避免二缓冲下必须等待下一消隐窗的帧率损失。
- `bsp_camera_in_vblank()` 供外部查询相位。

### 量化验证
- NDTR 采样序列：41 个采样中 8 个处于消隐期 ≈ 19.5% ≈ 16ms(帧周期 83ms)，有效读出期 67ms → 旧随机相位 memcpy 撕裂概率 ≈ 80%。
- 无主机模式 cam_snap 计数：cam_frame_count=128, cam_snap_ok=128, cam_snap_torn=0, cam_snap_ndtr0=ndtr1=0x7080(拷贝前后 DMA 计数器未动), cam_snap_cycles=1.49M(≈3.12ms << 16ms 窗口)。
- A/B 对照(手动曝光 0x3503=0x03 关 AEC, 0x3501=0x04↔0x60 使相邻帧 Y≈7↔120, 17 倍亮度差)：
  - GATED(修复后): 行亮度 spread=8.8, 最大行跳变 0.4 → 无拼接缝
  - UNSYNC(旧行为复现): 行亮度 spread=80.2, 最大行跳变 73.3 在 row 105→106 → 撕裂明确复现
