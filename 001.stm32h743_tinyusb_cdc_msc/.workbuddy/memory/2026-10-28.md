# 2026-10-28

## 「U 盘突然无法识别」根因：Windows USBSTOR 设备节点卡死（不是固件）

### 症状
- CDC 串口 COM7 正常，`USB 大容总存储设备` 接口也在，但**没有盘符**、`Get-Disk` 里也没有这块盘。
- 设备侧 `mtrace`：`MOUNT → CAP ×2 → 之后只有 TUR（每 1 s）`, **零 READ(10)**。
- 系统日志无 disk 事件 51、无 I/O 错误 —— 主机根本没读过扇区 0。

### 定位手法（可复用）
1. 先排除固件：把唯一改动（`CFG_TUD_MSC_EP_BUFSIZE` 512→4096）回退，**故障不变** → 与固件无关（这条否证很关键）。
2. 在 `msc_device.c` 的 CBW 处插入临时探针，把**每条 CBW 的 opcode/lun/blocks/bytes** 打进 sdcard 的 trace 环。
   得到的完整序列：`INQUIRY×2 → READ FORMAT CAPACITIES(0x23) → INQUIRY → READ CAPACITY(0x25) → MODE SENSE(6)(0x1A)×2 → 停`。
   全部被正确应答，没有 STALL、没有 REQUEST SENSE —— **设备侧 100% 干净**。
3. 转查 PnP：`USBSTOR\DISK&VEN_STM32H7&PROD_SD_CARD&REV_1.0\...` 节点 **Present=True / Problem=NONE / ConfigFlags=0 / Service=disk**，
   但 `DEVPKEY_Device_DevNodeStatus = 0x25174026`，**`DN_STARTED(0x8)` 没置位** → disk.sys 从未启动，所以一条 READ 都不会发。

### 处置（不碰 Windows 设置）
把 INQUIRY 的 **product revision `1.0` → `1.1`**。REV 是 USBSTOR 实例路径的一部分，
改它等于让 Windows 建一个全新 devnode → 立刻挂上 `G:`（FAT32, 32 GB, disk 4）。
> 教训：`PROD` / `REV` 字符串是「设备实例身份」，需要绕过卡死的 devnode 时改它最省事；
> 单纯 D+ 软断开 / SWD 复位 / 重新插线都**不会**重建 devnode，所以修不好。

### 嫌疑来源
本会话为测挂载耗时反复执行 `pnputil /disable-device` + `/enable-device`（复合设备父节点），
很可能就是它把 USBSTOR 子节点留成了 present-but-never-started。

### 冷挂载实测（新实例）
`325 ms MOUNT → 341..404 ms CAP×N → RD LBA0(MBR)/LBA2/LBA8192(BPB)/FAT`，**~404 ms 完成**，`last HAL SD error=0x0`。

### 已知遗留（未修）
- 设备端 FatFs 挂载失败：`FATFS code=0x0E (FR_NOT_READY)`。
  `diskio.c` 里 `DEV_RAM=0 / DEV_MMC=1`，而 `sd_app.c` 全程用 `"0:"` → 实际挂在 **RAM 盘**上，不是 SD 卡。`ls`/`cat` 因此不可用。
- 写吞吐差：PC 侧写 4 MB 用 27.8 s ≈ **147 KB/s**（读走主机缓存，测得值无意义）。
  512 B MSC 缓冲 = 每 512 B 一次 BOT 往返；4 KB 缓冲因上述节点故障未能验证，可重测。

## 两项修复：MSC 缓冲 32 KB + FatFs 卷号

### 1. 吞吐：瓶颈是「每笔传输固定开销」，不是 SD 总线

链路是 **Full Speed**（`BOARD_TUD_RHPORT=0` → OTG_FS PA11/PA12，12 Mbit/s，裸速率 1.2 MB/s），
所以 4 KB 数据在 USB 上就要 2.7 ms，加上卡内编程延迟（实测 4 ms）→ 每笔 ~7 ms。

设备侧轨迹可直接量：`WR → WROK` 4 ms（卡编程），`WROK → 下一个 WR` 3 ms（CSW + CBW + 数据）。

| `CFG_TUD_MSC_EP_BUFSIZE` | 写 | 读 |
|---|---|---|
| 512 B | 147 KB/s | 661 KB/s（旧，走主机缓存，仅参考）|
| 4 KB | 619 KB/s | 970 KB/s |
| **32 KB** | **911–921 KB/s** | **1010 KB/s** |

- 读从 4 KB 起就饱和在 ~1.01 MB/s ≈ FS 天花板，再加缓冲无收益。
- 写继续涨到 32 KB，翻到 64 KB **编译不过**：`msc_device.h` 有
  `TU_VERIFY_STATIC(CFG_TUD_MSC_EP_BUFSIZE < UINT16_MAX)`，所以 32768 是实用上限。
  代价 DTCM 20.7 KB → 49.4 KB（37.66%）。
- 埋点提醒：32 KB 缓冲下 8 MB 写入 = 256 笔，会瞬间冲掉 128 条的 trace 环，事后 dump 看不到 MOUNT/CAP。

### 2. FatFs 卷号：`FF_FS_RPATH=0` 时不带盘号的路径**固定走盘 0**

`sd_app.c` 原来用 `"0:"` → 盘 0 是 **RAM 盘**（`diskio.c`: `DEV_RAM=0 / DEV_MMC=1`），
所以 mount/mkfs/目录操作全落在 `0x24000000`，`FATFS code=0x0E`、`ls`/`cat` 永远失败。

改成 `SD_VOL "1:"` 后 mount 变成 `FATFS code=00`，但 `ls` 仍报 `opendir failed (fr=12 FR_NO_PATH)`：
**只改 mount 的盘号不够**。`f_opendir("/")` / `f_open("README.TXT")` 这些路径不带盘号，
而 `get_ldnumber()` 在 `FF_FS_RPATH == 0` 时直接 `return 0`，
`f_chdrive()` 只改 `CurrVol`、这个配置下**根本不被读取**（它只影响 `FF_FS_RPATH==1`）。
→ 落点：所有路径必须显式带盘号（`SD_VOL "/"`、`SD_VOL "/README.TXT"`），`cmd_cat` 里用
`snprintf(path, sizeof path, SD_VOL "/%s", rel)` 拼，并允许用户输入带不带前导 `/`。
（另一条路是把 `FF_FS_RPATH` 打开，但那会同时改变相对路径/cdir 语义，改动面更大。）

验证：`ls` 列出真实目录（BULK.BIN / rt.txt，中文名显示为 `?`），
`cat rt.txt` → `RT-2026-08-05-ROUNDTRIP-OK-7F3A9C`，`cat PC_TEST.TXT` → 主机写入的内容。
