## 编译结果（Keil AC6 / armclang V6.16）
```
UV4 -r stm32h743.uvprojx      → 0 Error(s), 0 Warning(s)   (245 文件全量重编)
Program Size: Code=304292 RO-data=168392 RW-data=205104 ZI-data=257448
```
| 区域 | Keil 实测 | 占比 | GCC(CMake) 对照 |
|---|---|---|---|
| FLASH (Load Region 实占) | 474576 B (`Objects/stm32h743.bin` 实测) | **22.63%** / 2MB | 345040 B / 16.45% |
| AXI SRAM (RW_IRAM1 @0x24000000) | 257752 B | **49.17%** / 512KB | 266260 B / 50.79% |
| SRAM_D2 (RW_IRAM3 @0x30000000) | 204800 B | **69.44%** / 288KB | 204800 B (`.ram_d2` NOLOAD) |
| SRAM_D3 / DTCM | 0 | — | 0 |

- FLASH 多出的 ~129KB **纯粹是 armclang `-O0` vs gcc `-Og` 的代码量差**，非配置差异。
- `glyph_cache.o` 的 `s_pool[200*1024] __attribute__((section(".ram_d2")))` 无初值，
  GCC 按 NOBITS 处理（NOLOAD，0 FLASH 代价），**armclang 却把它算作 RW Data 204800**。
  好在 ARM 链接器对 RW 初始化镜像做了压缩（204800 全零 → 约 1.6KB），`.bin` 未因此膨胀，属可接受。
- 启动时会多一次 200KB 清零拷贝，代价可忽略。scatter 里给 `RW_IRAM3` 加 `UNINIT` 可彻底对齐 GCC 语义（本次未改）。

## 关键坑：UV4 命令行 `-o` 日志路径必须用绝对路径
- `UV4.exe -b MDK-ARM/stm32h743.uvprojx -o MDK-ARM/keil_build.log` → **退出码 0 但日志文件根本不生成**（无论是相对路径、预建空文件、还是 cd 进 MDK-ARM 都一样）。
- 改成绝对 Windows 路径后正常写出：
  `UV4.exe -b "E:\...\MDK-ARM\stm32h743.uvprojx" -o "E:\...\MDK-ARM\keil_build.log"`
  （Git Bash 下调 UV4 需 `MSYS_NO_PATHCONV=1`，否则 `/c/...` 与反斜杠被转换。）
- **UV4 退出码静默性**：即使不写日志，`-b`/`-r` 仍会真的编译并更新 `Objects/*.o`、`.axf`、`Listings/*.map`。
  判断"到底编没编"要看 axf/map 的 mtime，不要只看退出码和日志。
- `-r` = 全量重建，`-b` = 增量；产物：`Objects/stm32h743.{axf,hex,bin}`（AfterMake 用 `fromelf --bin`）。
